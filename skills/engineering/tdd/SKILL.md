# 测试驱动开发

TDD 是 red → green 循环。本 skill 是让这个循环产出值得保留的测试的参考：什么是好测试、测试放在哪里、反模式，以及循环的规则。每一节在每个循环周期都适用——在循环之前和之中查阅它们，而不是之后。

探索代码库时，阅读 `CONTEXT.md`（如果存在），让测试名和接口词汇与项目的领域语言一致，并尊重你所触及区域的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而不是实现细节。代码可以完全改变；测试不应该。好测试读起来像一份规格说明——"user can checkout with valid cart" 准确告诉你存在什么能力——并且能在重构中幸存，因为它不关心内部结构。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

## Seam —— 测试放在哪里

**seam**（接缝）是你测试所在的公共边界：你观察行为而无需伸手进入内部的接口。测试位于 seam 处，绝不针对内部。

**只在预先约定的 seam 处测试。** 在编写任何测试之前，写下被测的 seam 并与用户确认。禁止在任何未确认的 seam 处编写测试。你不可能测试一切——预先约定 seam 是让测试投入落在关键路径和复杂逻辑上、而不是每个边缘情况上的方法。

问："公共接口是什么，我们应该测试哪些 seam？"

当接口本身的形态尚存疑问时——模块应该多深、seam 应该在哪里、接口应该暴露什么——使用 `/codebase-design` skill 的词汇。它是 module、interface、depth、seam、adapter、leverage 和 locality 这些术语的共享来源，它是一份供查阅的参考，而不是一个要运行的会话。

## 反模式

- **耦合实现** —— mock 内部协作者、测试私有方法，或通过旁路验证（查询数据库而不是使用接口）。识别信号：重构后行为没变但测试挂了。
- **同义反复** —— 断言用与代码相同的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、用同样方式手工推导的快照、断言一个常量等于它自己），因此它天然通过，永远不可能与代码产生分歧。期望值必须来自独立的真相来源——已知正确的字面量、手工演算的示例、spec。
- **水平切片** —— 先写所有测试，再写所有实现。批量测试验证的是_想象中的_行为：你测试的是事物的_形状_而不是面向用户的行为，测试对真实变化不敏感，而且你在理解实现之前就承诺了测试结构。改用**垂直切片**——一个测试 → 一个实现 → 重复，每个测试都是一颗 **tracer bullet**（曳光弹），响应上一个循环教给你的东西。

## 循环的规则

- **先红后绿。** 先写失败的测试，然后只写刚好让它通过的代码。不要预判未来的测试，不要添加投机性功能。
- **一次一个切片。** 每个循环一个 seam、一个测试、一个最小实现。
- **重构不是循环的一部分。** 它属于评审阶段（见 `code-review` skill），而不是 red → green 实现循环。

## 遇到困难时

| 问题 | 解决方案 |
|------|----------|
| 不知道怎么测试 | 写出你期望的 API。先写断言。问你的人类伙伴。 |
| 测试太复杂 | 设计太复杂。简化接口。 |
| 必须 mock 所有东西 | 代码耦合太紧。使用依赖注入。 |
| 测试 setup 太庞大 | 提取辅助函数。还是复杂？简化设计。 |

## 调试集成

发现 bug？写一个重现 bug 的失败测试。按 TDD 循环走。测试既证明了修复有效，又防止了回归。

绝不在没有测试的情况下修复 bug。
