# 性能分析与优化（Performance）

## 心态

- 编写代码时，若某种方式不会明显影响可读性或复杂性，就选更快的那种。
- 若开发大型系统时完全忽略性能，最终会得到到处都是瓶颈、却没有明显热点的系统——无从下手优化。把性能当一等公民，而不是事后补丁。
- 被他人使用的库、被大量使用的系统，一旦上线就很难做重大改动。这类代码早期就要认真对待性能。

## 分析流程

### 1. 先估算成本（order-of-magnitude estimate）

动手前先做数量级估算，建立「慢在哪」的直觉：

1. 统计各种低级操作的次数：磁盘读写、网络往返、传输字节数。
2. 每种昂贵操作的成本 × 数量，再求和。
3. 若关心延迟且系统有并发，部分成本会重叠，需要更复杂的分析来估算延迟。

常见操作的成本量级（用于快速心算）：

```
L1 cache reference                             0.5 ns
L2 cache reference                             3 ns
Branch mispredict                              5 ns
Mutex lock/unlock (uncontended)               15 ns
Main memory reference                         50 ns
Compress 1K bytes with Snappy              1,000 ns
Read 4KB from SSD                         20,000 ns
Round trip within same datacenter         50,000 ns
Read 1MB sequentially from memory         64,000 ns
Read 1MB over 100 Gbps network           100,000 ns
Read 1MB from SSD                      1,000,000 ns
Disk seek                              5,000,000 ns
Read 1MB sequentially from disk       10,000,000 ns
Send packet CA->Netherlands->CA      150,000,000 ns
```

读表的要点：缓存未命中比算术贵几个数量级，网络往返比内存贵几千倍。「优化」多数时候是减少这类昂贵操作，而不是让廉价算术更快。

### 2. 剖析定位（profile）

用数据说话，不要靠猜。首选 pprof（本地和生产都好用，提供详细高层信息）；需要更细时用 perf。

- 生成带适当调试信息和优化的生产版本二进制，剖析结果才可信。
- 为要改进的代码写微基准测试：缩短优化迭代时间、验证效果、防止未来退化。
- 用基准测试库获取性能计数器，提高测量精度。
- 锁争用会让 CPU 使用率人为下降，注意从锁的角度分析。

### 3. profiles 空洞时怎么办

CPU 看起来正常、没有明显元凶——通常是所有易解问题都解决之后的情形。此时：

- 别低估细微优化：各子系统分别做 2% 的优化，累积起来相当可观。这类优化靠稳定、高质量的微基准衡量。
- 找调用栈顶部的循环结构（CPU 火焰图里最容易定位）。这些循环往往能通过重新设计提高效率。
- 退一步看调用栈上层，做结构性的改变——这正是「算法改进」的用武之地。
- 警惕过度通用的代码：换成更定制或更低层的实现。例如反复用正则做前缀匹配的，改用简单字符串前缀匹配。
- 减少内存分配：先抓分配数据，再重点砍掉分配次数最多的因素。
- 收集硬件性能指标，找出缓存命中率低的功能。

### 4. 验证

优化后重新剖析，确认热点消失；用微基准守住回归。

## 优化技术目录

按杠杆从高到低排列。每类技术的共同逻辑是：**减少昂贵的操作**（缓存未命中、内存分配、网络/磁盘、锁、重复计算），而不是让廉价操作更快。

### 算法改进

提升性能的最大机会。例如 O(N²) → O(N log N)/O(N)；Map（O(log N)）→ 哈希表（O(1)）。结构稳定的代码里这类机会少，但写新代码时值得优先考虑。

### 内存表示

仔细设计重要数据结构的缓存占用，往往带来显著提升。收益：(a) 减少缓存未命中；(b) 降低内存总线负载，让本程序和同机其他程序都更快。

- **紧凑数据结构**：频繁访问或占内存大的数据用紧凑存储，少访问缓存行、降总线带宽。注意缓存行竞争。
- **内存布局**：重排字段减少对齐间隙；小数据用小数值类型；经常一起访问的字段放一起；只读字段与可写字段分开存放（写可写字段时不会把只读字段挤出缓存）；冷数据移开（放末尾、间接存储或单独数组），不与热数据混放。
- **用索引而非指针**：64 位指针占 64 bit，大量指针的间接引用既耗内存又破坏局部性。改用整数索引访问数组，元素连续存储、缓存利用率高。
- **批量存储**：避免每个元素单独对象的数据结构（std::map/unordered_map），选连续存储的（std::vector、absl::flat_hash_map）——缓存好、分配开销低。
- **避免嵌套映射**：嵌套映射可用复合键单层映射替代（btree<a,btree<b,c>> → btree<pair<a,b>,c>），显著降低查找/插入成本。若第一个键尺寸大，嵌套可能更合适。
- **用数组而非映射**：域的整数/枚举范围小、或元素极少时，用数组/向量替代映射。

### 减少内存分配

分配的额外成本：分配器时间、新对象的初始化/销毁、以及每次分配通常落在新缓存行上（数据分散 = 缓存空间浪费）。

- **避免不必要的分配**：能用静态分配的零向量就不要先分配再填零；作用域受限的对象用栈分配（大对象注意栈帧）。
- **resize / reserve**：预先知道最大或预期大小时，提前为容器分配空间。
- **避免复制**：移动而非复制；临时结构里存指针/索引而非完整副本。
- **复用临时对象**：循环内声明的容器每轮都重建，移到循环外。注意 protobuf/string/vector 等会膨胀到历史峰值，定期重建可以回收内存。

### 避免不必要的工作

提升效率最直接的办法是少做不必要的事：

- 为常见情况写专门代码路径（快速路径）；提前计算；把任务推迟到真正需要时；把操作挪到低频执行路径；用缓存避免重复工作。

**让编译器的任务更简单**（仅在剖析显示有问题时做，编译器通常能自己解决；看热点函数的汇编判断它是否处理得当，pprof 可直观展示源码/汇编/性能数据）：

- 避免高频调用的函数里再有函数调用（省去框架设置开销）。
- 把慢路径代码移到单独的尾调用函数。
- 数据会被后续多次重用时，先少量复制到本地变量——编译器可假定无别名，利于自动向量化和寄存器分配。

**降低数据收集成本**：维护统计数据有成本，按需降采样。不要在频繁执行的路径上打印日志——日志记录本身有开销，即使什么都没记。

### 并行化与同步

- **利用并行**：耗时任务分块并行、再合并结果。先分组再并行，避免每任务单独并行的额外成本。
- **保持临界区简短**：避免在锁内做复杂操作，尤其小心貌似无害却会隐式远程调用或访问文件的代码，以及解锁前执行的高成本析构（~MutexUnlock 场景）。
- **分片减少竞争**：竞争激烈的互斥保护结构，若无一致性约束，可拆成多个子结构各自上锁；map 类结构改用并发 hash map。
- **SIMD**：探索用现代 CPU 的 SIMD 指令同时处理多个数据项。
- **减少上下文切换**：小任务在内存内内联处理，而不是丢给设备线程池。
- **buffered channels 流水线**：无缓冲 channel 适合同步控制，不适合提升并行处理能力。
- **无锁方案**：无锁结构可能更高效，但直接操作原子变量很危险——用更高级的抽象层。

### API 设计

被广泛使用的 API 面临不断增加新功能的压力。加新功能要谨慎：会限制未来的开发方式，也给不需要的用户带来成本。

- **批量接口**：提供批量处理，减少昂贵 API 调用，或利用算法改进。
- **预分配/预计算参数**：高频例程让上层调用者传入他们已有的数据，避免底层自己分配临时结构或重算已有信息。
- **线程兼容 vs 线程安全**：默认做到线程兼容（外部同步），让不需要同步的用户不付成本；若类型典型用法就需要同步，则同步放类型内部，便于后续调优（如分片减少竞争）而不影响调用方。

### Protocol Buffer

protobuf 用起来方便，但性能开销大——一例：1000 个点求 Y 坐标和，protobuf → C++ vector 后快 20 倍；protobuf 版本还会在二进制里加几千字节代码和数据，积少成多，增加 I/D 缓存负担。

- 不必需时别用：进程内模块间直接用 struct/vector。
- 二进制数据或大数值用 bytes 而非 string。
