# 深化（Deepening）

如何在依赖已定的前提下，安全地深化一个由浅模块组成的簇。默认你已掌握 [SKILL.md](SKILL.md) 中的词汇——**module**、**interface**、**seam**、**adapter**。

## 依赖分类

评估一个深化候选时，先对它的依赖分类。类别决定了深化后的模块如何跨 seam 测试。

### 1. 进程内（In-process）

纯计算、内存状态、无 I/O。永远可以深化——合并模块，直接通过新接口测试。不需要 adapter。

### 2. 本地可替代（Local-substitutable）

有本地测试替代品的依赖（Postgres 用 PGLite、内存文件系统）。只要替代品存在就可以深化。深化后的模块在测试套件中带着替代品一起测试。seam 在内部；模块的外部接口上不需要 port。

### 3. 远程但自有（Ports & Adapters）

跨网络边界的自有服务（微服务、内部 API）。在 seam 处定义一个 **port**（接口）。深模块拥有逻辑；传输层作为 **adapter** 注入。测试用内存 adapter，生产用 HTTP/gRPC/队列 adapter。

建议的表述形状：*「在 seam 处定义一个 port，为生产实现一个 HTTP adapter、为测试实现一个内存 adapter，这样即使部署跨越网络，逻辑也安放在一个深模块里。」*

### 4. 真正的外部依赖（Mock）

你无法控制的第三方服务（Stripe、Twilio 等）。深化后的模块把外部依赖作为注入的 port 接收；测试提供 mock adapter。

## seam 纪律

- **一个 adapter 意味着假想的 seam，两个 adapter 才意味着真实的 seam。** 除非至少有两个 adapter 是合理的（通常是生产 + 测试），否则不要引入 port。单 adapter 的 seam 只是间接层。
- **内部 seam vs 外部 seam。** 深模块除了在接口处的外部 seam 之外，还可以有内部 seam（私属于实现，供自己的测试使用）。不要因为测试用了内部 seam，就把它们通过接口暴露出去。

## 测试策略：替换，而非叠加

- 一旦深化后模块的接口上有了测试，旧的浅模块单元测试就变成了废物——删掉它们。
- 在深化后模块的接口上写新测试。**接口就是测试表面。**
- 测试通过接口断言可观察的结果，而不是内部状态。
- 测试应当能在内部重构中存活——它们描述的是行为，不是实现。如果实现一变测试就得改，那它测到了接口之后。
