# Design It Twice（设计两遍）

当用户想为选定的深化候选探索备选接口时，使用这个并行 sub-agent 模式。基于 "Design It Twice"（Ousterhout）——你的第一个想法不太可能是最好的。

使用 [SKILL.md](SKILL.md) 中的词汇——**module**、**interface**、**seam**、**adapter**、**leverage**。

## 流程

### 1. 框定问题空间

在启动 sub-agent 之前，为选定的候选写一份面向用户的问题空间说明：

- 任何新接口都需要满足的约束
- 它会依赖的东西，以及这些依赖属于哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一份粗略的示例代码草图，用来把约束落到实处——不是提案，只是让约束变得具体的一种方式

把它展示给用户，然后立刻进入第 2 步。用户边读边想，sub-agent 同时在并行工作。

### 2. 启动 sub-agent

并行启动 3 个以上的 sub-agent。每个都必须为深化后的模块产出一个**截然不同**的接口。

给每个 sub-agent 一份独立的技术简报（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、seam 背后是什么）。这份简报独立于第 1 步中面向用户的问题空间说明。给每个 agent 一个不同的设计约束：

- Agent 1："最小化接口——目标是最多 1–3 个入口点。最大化每个入口点的 leverage。"
- Agent 2："最大化灵活性——支持多种用例和扩展。"
- Agent 3："为最常见的调用方优化——让默认情形平凡到不能再平凡。"
- Agent 4（如适用）："围绕 ports & adapters 设计跨 seam 依赖。"

简报中要同时包含 [SKILL.md](SKILL.md) 的词汇和 CONTEXT.md 的词汇，这样每个 sub-agent 的命名都与架构语言和项目的领域语言保持一致。

每个 sub-agent 输出：

1. 接口（类型、方法、参数——外加不变量、顺序、错误模式）
2. 展示调用方如何使用它的用法示例
3. 实现藏在 seam 背后的东西
4. 依赖策略与 adapter（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡——哪里 leverage 高，哪里单薄

### 3. 展示与比较

逐个展示设计，让用户能消化每一个，然后用散文形式做比较。从 **depth**（接口处的 leverage）、**locality**（变更集中在何处）和 **seam 位置**三个维度对比。

比较之后给出你自己的推荐：你认为哪个设计最强、为什么。如果不同设计的元素能很好地组合，就提出一个混合方案。要有主见——用户要的是一个有力的判断，不是一份菜单。
