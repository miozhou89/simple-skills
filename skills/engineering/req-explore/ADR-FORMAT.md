# ADR 格式

ADR 存放在 `docs/adr/`，使用顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。

惰性创建 `docs/adr/` 目录——只在需要第一个 ADR 时创建。

## 模板

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

就这些。ADR 可以只有一段话。价值在于记录*做了*一个决定以及*为什么*——而不是填满各个栏目。

## 可选栏目

只在真正增值时才包含这些。大多数 ADR 用不上。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——当决策会被重新审视时有用
- **Considered Options** — 只在被否决的备选方案值得记住时
- **Consequences** — 只在有非显而易见的下游影响需要点出时

## 编号

扫描 `docs/adr/` 中已有的最大编号，加一。

## 何时提议 ADR

以下三条必须全部成立：

1. **难以逆转** — 日后改主意的代价是有分量的
2. **没有上下文会令人意外** — 未来的读者看着代码会好奇"他们到底为什么这么做？"
3. **真实权衡的产物** — 确实存在过真正的备选方案，而你出于具体原因选了其中一个

如果一个决定容易逆转，跳过它——你反正会逆转它。如果它不令人意外，没人会好奇为什么。如果没有真正的备选方案，那除了"我们做了显而易见的事"之外也没什么可记的。

### 什么够格

- **架构形态。** "我们用 monorepo。" "写模型是 event-sourced 的，读模型投影进 Postgres。"
- **context 之间的集成模式。** "Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。"
- **带来锁定的技术选型。** 数据库、消息总线、认证提供商、部署目标。不是每个库都算——只算那些换掉要花一个季度的。
- **边界与范围决策。** "Customer 数据归 Customer context 所有；其他 context 只通过 ID 引用它。" 明确的"不"和"是"一样有价值。
- **刻意偏离显而易见的路径。** "我们用手写 SQL 而不是 ORM，因为 X。" 任何合理读者会默认相反做法的地方。这类 ADR 能阻止下一位工程师去"修"一个刻意为之的东西。
- **代码里看不见的约束。** "因为合规要求，我们不能用 AWS。" "响应时间必须在 200ms 以内，因为合作方 API 合同如此约定。"
- **否决理由非显而易见的被否决方案。** 如果你考虑过 GraphQL 却因微妙原因选了 REST，记下来——否则六个月后还会有人再提 GraphQL。
