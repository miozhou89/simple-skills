# 原型

原型是**回答某个问题的一次性代码**。问题决定形态。

## 选择分支

识别正在回答的是哪个问题——从用户的提示、周边代码中判断，如果用户在场就直接问：

- **"这个逻辑/状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个可分享的单 HTML 文件——自由操作的按钮加标签页式引导演练——把状态机推过那些纸面上难以推理的情形，并且非开发者也能操作。
- **"这个应该长什么样？"** → [UI.md](UI.md)。在单个路由上生成几个截然不同的 UI 变体，通过 URL 搜索参数和悬浮底栏切换。

两个分支产出的工件非常不同——选错了会浪费整个原型。如果问题确实含糊且联系不上用户，默认选与周边代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部声明该假设。

## 两个分支都适用的规则

1. **从第一天起就是一次性的，并明确标注。** 把原型代码放在它实际将被使用的位置附近（紧挨它所原型化的模块或页面），让上下文显而易见——但命名要让随意的读者一眼看出这是原型、不是生产代码。对于一次性 UI 路由，遵循项目已有的路由约定；不要发明新的顶层结构。
2. **运行起来要毫不费力。** UI 原型从项目任务运行器中的一条命令启动——`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是一个用户双击即可打开的单 HTML 文件。无论哪种，启动都不需要动脑子。
3. **默认不做持久化。** 状态存在内存里。持久化恰恰是原型要_验证_的东西，而不是它应依赖的东西。如果问题明确涉及数据库，就指向一个临时 DB 或本地文件，并起一个明确的 "PROTOTYPE — wipe me" 名字。
4. **跳过打磨。** 不写测试，不做超出让原型_能跑起来_所需的错误处理，不做抽象。重点是快速学到东西。
5. **把状态暴露出来。** 每次操作之后（逻辑）或每次切换变体时（UI），打印或渲染完整的相关状态，让用户看到什么变了。
6. **完成后留存。** 把任何已验证的决策融入真实代码，然后把原型本身作为 **primary source** 留存：提交到一个一次性分支，脱离 main，并在实现工单上留下指向该分支的上下文指针。答案也要留存——结论和它回答的问题——记录在工单或提交中。main 分支只保留已验证的决策。
