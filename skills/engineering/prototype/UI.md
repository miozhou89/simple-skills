# UI 原型

在单个路由上生成**几个截然不同的 UI 变体**，通过悬浮底栏切换。用户在浏览器中来回翻看变体，选一个（或从每个中各取所需），然后把其余的全部扔掉。

如果问题关乎逻辑/状态而非外观——走错分支了。用 [LOGIC.md](LOGIC.md)。

## 何时适用这种形态

- "这个页面应该长什么样？"
- "定下来之前我想看看这个仪表盘的几种方案。"
- "给设置界面试个不同的布局。"
- 任何用户否则要在脑中三个模糊草图之间纠结一天的场合。

## 两种子形态——强烈优先子形态 A

当 UI 原型**与应用其余部分贴在一起**时会容易评判得多——真实的页头、真实的侧边栏、真实的数据、真实的密度。孤立的一次性路由是真空：每个变体单独看都不错。只要存在一个合理的现有页面可以承载变体，就默认用子形态 A。只有当原型确实没有邻近的容身之处时才用子形态 B。

### 子形态 A——对现有页面的调整（优先）

路由已存在。变体渲染在**同一路由**上，由 `?variant=` URL 搜索参数门控。现有的数据获取、参数和认证全部保留——只有渲染部分被替换。这是默认项；除非有明确理由，否则选它。

如果原型针对的东西还没有页面、但*自然会存在于某个页面之内*（仪表盘的新区块、设置界面的新卡片、现有流程的新步骤）——那仍然是子形态 A。把变体挂载进宿主页面。

### 子形态 B——新页面（最后手段）

仅当被原型化的东西确实没有可寄居的现有页面时使用——例如一个全新的顶层界面，或一个无法合理嵌入任何地方的流程。

创建一个**一次性路由**，遵循项目已有的路由约定——不要发明新的顶层结构。命名要让人一眼看出是原型（例如在路径或文件名中包含 `prototype` 一词）。同样的 `?variant=` 模式。

在定下来用子形态 B 之前，先自检：真的没有任何现有页面可以嵌入它吗？空路由会隐藏有内容页面才会暴露的设计问题。

两种子形态中，悬浮底栏完全相同。

## 流程

### 1. 陈述问题并选定 N

默认 **3 个变体**。超过 5 个就不再是截然不同，而开始变成噪音——以此封顶。

用一行话写下计划，放在原型所在位置或文件顶部注释里：

> "Three variants of the settings page, switchable via `?variant=`, on the existing `/settings` route."

无论用户是否在场反驳，这都有效。

### 2. 生成截然不同的变体

起草每个变体。每个都要满足：

- 页面的用途和它可访问的数据。
- 项目的组件库/样式系统（TailwindCSS、shadcn、MUI、纯 CSS，不管是什么）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**——不同的布局、不同的信息层级、不同的主要操作点，而不只是不同颜色。三个微调过的卡片网格不是 UI 原型，是墙纸。如果两个草稿出来太相似，就带着明确的 "不许用卡片网格" 指示重做一个。

### 3. 把它们接起来

在路由上创建一个切换组件：

```tsx
// pseudo-code — adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：把所有现有数据获取保留在切换器之上；只有被渲染的子树随变体改变。

子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载同一个切换器。

### 4. 构建悬浮切换器

一个固定在屏幕底部中央的小条，由三部分组成：

- **左箭头**——切到上一个变体（循环回绕）。
- **变体标签**——显示当前变体键，以及（如果变体导出了名字）名字。例如 `B — Sidebar layout`。
- **右箭头**——向前切换（循环回绕）。

行为：

- 点击箭头更新 URL 搜索参数（用框架的路由器——Next 上 `router.replace`，React Router 上 `navigate`，等等），使变体可分享、刷新后保持稳定。
- 键盘：`←` 和 `→` 方向键也可切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 处于焦点时，不要拦截方向键。
- 视觉上与页面区分开（例如高对比度的胶囊形、细微阴影），让人一眼看出它不是被评估设计的一部分。
- 在生产构建中隐藏——用 `process.env.NODE_ENV !== 'production'` 或等价检查门控，使误合并的原型不会把底栏带给用户。

把切换器放进单个共享组件，让两种子形态都能复用。放在项目中共享 UI 所在的位置。

### 5. 交付

给出 URL（以及 `?variant=` 各键）。用户有空时会翻看。最有意思的反馈通常是 **"我想要 B 的页头配 C 的侧边栏"**——那才是他们真正想要的设计。

### 6. 留存答案并清理

某个变体胜出后，留存答案——哪个变体、为什么——然后按 [SKILL](SKILL.md) 描述的方式留存原型。把胜者融入真实代码，把其余的移到一次性分支，而不是进 main：

- **子形态 A**——把胜者融入现有页面；从 main 中删除落选变体和切换器。
- **子形态 B**——把胜出变体提升为正式路由；从 main 中删除一次性路由和切换器。

完整的变体集合是 primary source，所以它落在一次性分支而不是回收站——留在 main 分支的变体组件和切换器会迅速腐烂，并迷惑下一个读者。

## 反模式

- **只在颜色或文案上有差别的变体。** 那是微调，不是原型。真正的变体在结构上就有分歧。
- **变体之间共享太多代码。** 共享 `<Header>` 可以；共享 `<Layout>` 就违背了目的。每个变体都应能自由抛弃布局。
- **把变体接到真实的变更操作上。** 只读原型没问题。如果某个变体需要变更数据，指向一个桩——问题是 "这个应该长什么样"，不是 "后端能不能工作"。
- **把原型直接提升进生产。** 变体代码是在原型约束下写的（无测试、错误处理极少）。融入时要正经重写。
