# image to code

## 检测框架

按配置文件确定框架，使用相应语言、组件扩展名与页面位置：

| 配置文件 | 框架 | 组件扩展名 | 页面位置 |
|-------------|-----------|---------------|---------------|
| `lv_conf.h` | LVGL | `.cpp` | `src/gui/` |
| `astro.config.*` | Astro | `.astro` / `.tsx` | `src/pages/` |
| `next.config.*` | Next.js | `.tsx` | `app/` 或 `pages/` |
| `vite.config.*` + react | React/Vite | `.tsx` | `src/` |
| `remix.config.*` | Remix | `.tsx` | `app/routes/` |
| `nuxt.config.*` | Nuxt | `.vue` | `pages/` |
| `angular.json` | Angular | `.component.ts` | `src/app/` |

## 扫描与复用

生成代码前，扫描 `src/` 及 `public/`、`assets/`：
- 可复用组件（Button、Card、Input、Badge、Modal）与布局组件（Container、Grid、Section、Wrapper）
- 动画模式、工具函数、主题令牌（颜色、间距、字体）
- 已有资源的命名约定

**禁止复制重复：** 存在匹配组件时扩展它而非新建；页面有多个相似 UI 元素时提取为公共组件。

## 干净分析标准

干净且系统化地分析。

禁止做模糊的、只看氛围的分析。
禁止过快地直接从图像跳到代码。

对于每张生成的分区图像，干净地检查：
- 这个分区是什么
- 视觉优先级是什么
- 什么文字是可读的
- 什么字体关系是可见的
- 什么间距关系是可见的
- 什么按钮和控件是可见的
- 什么 card 或区块逻辑是可见的
- 什么颜色占主导
- 什么结构节奏是可见的
- 什么细节仍然不清楚


## 深度图像分析要求

在实现任何东西之前，深入分析生成的图像。

禁止只是扫一眼。
把它们当作设计规格说明来对待。

仔细检查并提取：
- 可读处的精确可见文字
- hero 主标题措辞
- 副标题措辞
- CTA 措辞
- 分区标题
- 字体特征
- 字号比例关系
- 字体气质
- 行数
- 换行行为
- 对齐逻辑
- 分区间距
- 内部间距
- 内边距和栏间距
- card 尺寸和节奏
- border radius 逻辑
- stroke / 分隔线用法
- 按钮形状
- 按钮层级
- 按钮内边距
- 若在视觉上有所暗示的 hover 样式
- 色板
- 强调色
- 背景处理
- 图像处理
- 图标处理
- shadow / 深度逻辑
- grid 逻辑
- layout 结构
- 分区顺序
- 分区密度
- 视觉节奏
- 定义设计语言的重复母题

你的目标是准确理解为什么生成的UI看起来很强。

只有在这番深度分析之后，你才应该实现前端。

## 反嵌套盒子规则

禁止默认使用盒中盒中盒的 layout。

避免：
- 包裹一切的巨型圆角分区容器
- 大 card 里套中 card 再套外 card
- 毫无理由的仪表盘式隔间堆叠
- 让 layout 显得被困住的嵌套盒式 UI
- 只是一大块带边框面板、里面装着更多带边框面板、再装着更多带边框面板的分区

只在盒子有明确目的时使用盒子。

优先：
- 开放 layout
- 更清晰的留白
- 更少但更强的容器
- 合适处更扁平化的层级
- 直接的对齐和间距，而不是过度围合
- 一个主要的框架手法，而不是许多层叠框架

一个分区不应该像容器的牢笼。
它应该感觉是有设计的、开放的、有意为之的。

---

## 减少微 UI 杂乱规则

禁止用并不能实质改善清晰度的微小 UI 附加物弄乱设计。

避免：
- 不必要的胶囊
- 伪系统标记
- 虚假控件标签
- 装饰性代码风格标签
- 无意义的微小元数据行
- 填充性碎片标签
- 到处都是微小 badge
- 虚假仪表盘术语
- 分散主 layout 注意力的过度设计标签

除非确实必要，否则应避免的事例：
- 「00 orchestration layer」
- 微小的技术状态胶囊
- 装饰性运行时标记
- 过度具体的伪企业微文案
- 仅为了显得复杂而存在的填充性操作员 / 控制室标签

优先：
- 更干净的标题
- 更少的标签
- 真实的层级
- 更清晰的间距
- 更简洁的辅助文字
- 用更强的字体替代装饰性杂乱


## 文字提取规则

当生成的分区图像中文字可读时，提取并使用它，生成项目对应的多国语言翻译。

尤其要检查并提取：
- hero 主标题
- hero 副标题
- CTA 标签
- 分区标题
- 定价标签
- 功能名称
- 若清晰展示的评价者姓名和职位
- navbar 标签
- 如相关则 footer 标签

如果文字太小而无法可靠提取：
- 生成一张更近的提取图像
- 或生成该分区更清晰的第二版

禁止忽略文字提取。
可见文字是设计系统的一部分，应该影响实现。

---

## 字体提取规则

禁止只注意到字体「看起来不错」。
要正确地分析它。

提取并观察：
- 字号关系
- 字重关系
- 行数
- 行高感觉
- tracking 感觉
- serif vs sans 行为
- display font vs 正文的对比度
- 分区标题节奏
- CTA 文字比例
- 设计使用平静还是激进的字体

在实现期间使用这些发现。
禁止把字体扁平化成一个泛泛的编码层级。

---

## 间距提取规则

刻意地分析间距。

检查：
- 主标题与副标题之间的距离
- 文字与按钮之间的距离
- card 之间的距离
- 分区顶部和底部的间距
- 两侧栏间距
- card 内边距
- 图像到文字的距离
- navbar 间距
- CTA 区块间距
- 各分区之间的整体节奏

目标不是精确的像素 OCR。
目标是忠实的间距逻辑。

如果生成的设计更宽松，禁止把实现坍缩成泛泛的紧凑间距。

---

## 按钮 / component 提取规则

按钮和 component 必须被分析，而不是猜测。

检查：
- 按钮尺寸
- 按钮形状
- 按钮 radius
- 实心 vs 描边行为
- 图标用法
- hover 暗示的气质
- 主次层级
- card 结构
- badge 用法
- 分隔线
- shadow
- 边框
- 胶囊逻辑
- 如存在则输入框样式

如果按钮或 card 细节太小，生成一张更近的图像。

---

## 颜色提取规则

积极分析并从生成的图像中提取颜色。

检查：
- 背景色
- 面板颜色
- 强调色
- 按钮填充色
- 文字颜色层级
- 边框颜色逻辑
- shadow 颜色气质
- 图像色调 / 调色
- gradient 的克制或强度

实现的UI应该尽可能合理地保留原始的颜色逻辑。

禁止用泛泛的默认网页颜色替换精心设计的色板。

---

## 设计到代码的复制纪律

在生成并分析参考图像之后，以面向复制的方式实现UI。

这意味着：
- 紧密跟随参考图
- 保留 layout 逻辑
- 保留间距节奏
- 保留分区顺序
- 保留文字 / 图像平衡
- 保留字体气质
- 保留 component 风格
- 保留整体视觉清洁度

禁止在实现期间漂移到不同的设计方向。
禁止用泛泛的编码 layout 替换设计来「改进」它。

目标不是：
- 受图像启发

目标是：
- 视觉上忠实于图像，翻译成真实前端

---

## 反漂移实现规则

一种常见的失败模式是设计漂移：
图像看起来很强，但编码结果变得泛泛。

严格避免这一点。

在实现期间：
- 禁止简化成默认模板
- 禁止用泛泛的行替换独特的分区
- 禁止把宽松的间距压缩成密集 layout
- 禁止用平淡的层级替换强烈的字体
- 禁止为了图省事移除页面的视觉身份
- 禁止把分区逻辑合并成源图像中并不存在的重复模式
- 禁止重新引入在分析阶段被有意移除的嵌套盒子复杂度

最终编码结果应该仍然感觉与生成的参考图是同一个UI。

---

## 缺失细节解决

从图像实现时，有些细节可能仍然不清楚。

按以下顺序解决模糊之处：
1. 保留可见的设计语言
2. 保留 layout 和间距逻辑
3. 保留 component 家族
4. 保留气质和精致程度
5. 如需要则生成一张额外的细节图像
6. 如需要则把该分区重新生成为一张全新的独立图像
7. 只有在此之后，才选择最便于实现且忠实的版本

禁止过快用泛泛默认值填补模糊之处。

## 反 AI 垃圾规则

除非明确要求，否则严格避免这些模式。

### Layout 垃圾
- 一张巨大不可读的拼贴
- 无穷无尽的居中分区
- 逐分区重复的相同 card 行
- 克隆的左文右图区块
- 没有层级的虚假复杂度
- 无目的的装饰性空白
- card 套 card 套 card
- 包裹一切的巨型圆角分区
- 过度隔间化的仪表盘框架

### 视觉垃圾
- 默认的紫 / 蓝 AI gradient
- 过多的发光边缘
- 到处漂浮的色块
- 毫无理由堆叠的玻璃拟态
- 无结构的随机未来感细节
- 掩盖 layout 的过度 render 噪点

### 字体垃圾
- 巨型标题 + 弱小的副文案
- 过多的字体气质
- 别扭的断行
- 到处懒散地全大写
- 泛泛的 gradient 标题花招

### 内容垃圾
避免泛泛的填充式氛围词，例如：
- unleash
- elevate
- revolutionize
- next-gen
- seamless
- transformative platform

避免虚假品牌垃圾：
- Acme
- Nexus
- Flowbit
- Quantumly
- NovaCore

避免虚假复杂度垃圾：
- 伪企业控件标签
- 装饰性系统标记
- 填充式状态微文案
- 除非真正是该品牌的核心，否则不使用虚假的操作员 / 运行时 / 编排术语

### 密度垃圾
- 过满的分区
- card 过载
- 主分区之间微小的间距
- 视觉上令人疲惫的内容墙

---

## 字体优先纪律

字体是主要的设计材料。

总是确保：
- 清晰的大小对比度
- 明显的阅读顺序
- 强烈的 display font 时刻
- 可读的正文文字
- 简洁的文案
- 强化结构的分区标题

对于编辑风方向：
- 让字体塑造构图

对于技术 / 产品方向：
- 让字体传达信任和精确

---

## 分区节奏规则

高端UI不会让人感觉是同一个区块永远重复。

通过改变以下方面来变化整页的分区节奏：
- 密度
- 文字与图像比例
- 对齐
- 尺度
- 留白
- card 分组
- 背景强度
- 视觉速度

但是：
- 保持页面连贯
- 保持间距受控
- 避免随机跳跃
- 保持每个分区足够干净以便良好分析

## 密度与间距纪律

禁止把UI做得过于密集。

页面应该透气。

规则：
- 使用均匀的分区间距
- 保持主分区之间的大间隙受控且刻意
- 允许留白创造平静感
- 避免一个分区显得局促而下一个显得空旷
- 较小的分区仍然应该有足够的周边空间
- 优先可分析的宽松间距，而不是压缩构图
- 禁止用额外 UI 填满每一块可用区域
- 让简洁完成一部分设计工作

优质UI应该让人感觉：
- 开放
- 有构图
- 平衡
- 自信
- 透气

而不是：
- 局促
- 嘈杂
- 不均匀
- 过满
- 视觉上令人疲惫

## 生成代码

基于图片与检测到的框架生成代码。

整页 → 创建页面文件及所有区块组件
单个组件 → 仅创建该组件

资源匹配：
- 优先使用框架已有或内置的资源，如图标字体（例如 LVGL 中的 `LV_SYMBOL_*`）。
- 所需资源不存在时，改用占位符并添加注释说明，禁止编造资源路径。

标记完成前，必须对照设计稿截图校验最终 UI。

## 校验清单

- [ ] 布局一致（间距、对齐、尺寸）
- [ ] 排版一致（字体、字号、字重、行高、圆角）
- [ ] 颜色（含背景色）完全一致
- [ ] 交互状态按设计工作（hover、active、disabled）
- [ ] 响应式行为遵循 UI/UX 设计约束
- [ ] 资源正确渲染
- [ ] 满足无障碍标准

## 硬性规则

- 禁止安装新依赖，禁止基于假设实现——始终参考所提供图片的细节
- 复用优先：绝不重复创建已有组件
- 始终保留已有代码模式；所有生成的代码必须生产就绪

完成后询问"这符合你的预期吗？"，不支持则按反馈局部重新生成。
