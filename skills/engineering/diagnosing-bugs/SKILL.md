# 诊断 Bug（Diagnosing Bugs）

一套针对疑难 bug 的纪律。只有明确有理由时才跳过阶段。

探索代码库时，读 `CONTEXT.md`（如果存在）以建立相关模块的清晰心智模型，并检查你触碰区域内的 ADR。

## 脱敏（Redact）

本 skill 会让你展示命令、输出和捕获的工件。**先脱敏每一个秘密**——在原地写 `<REDACTED>`。反馈循环要基于环境变量构建，让凭据留在环境里，而不是留在你展示的东西里。捕获的工件带有 auth header：只引用携带信号的行。

如果脱敏后的输出不足以诊断 bug，明说，并向用户求助。

## 阶段 1 — 构建反馈循环

**这就是本 skill 的本体。** 其他一切只是机械动作。如果你有一个针对这个 bug 的**紧凑**通过/失败信号——一个能在*这个* bug 上变红的信号——你迟早会找到原因；二分、假设检验、插桩全都只是消费它而已。如果你没有，盯着代码看多久都救不了你。

在这里投入不成比例的精力。**要激进。要有创造力。拒绝放弃。**

### 构建方法——大致按此顺序尝试

1. **失败测试**，写在任何够得着 bug 的 seam（接缝）上——单元、集成、e2e。
2. **Curl / HTTP 脚本**，打向一个运行中的开发服务器。
3. **CLI 调用**，用夹具输入，把 stdout 与已知良好的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，断言 DOM/console/network。
5. **重放捕获的 trace。** 把真实的网络请求 / payload / 事件日志存到磁盘；在隔离环境中把它重放过代码路径。
6. **一次性 harness。** 拉起系统的最小子集（一个服务、mock 依赖），用一次函数调用触发 bug 代码路径。
7. **属性 / 模糊循环（Property / fuzz loop）。** 如果 bug 是「有时输出错误」，跑 1000 个随机输入，找失败模式。
8. **二分 harness。** 如果 bug 出现在两个已知状态之间（commit、数据集、版本），把「在状态 X 启动、检查、重复」自动化，好让你能 `git bisect run`。
9. **差分循环。** 让同一份输入分别走过旧版本与新版本（或两套配置），diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须有人类点击，用 `scripts/hitl-loop.template.sh` 驱动*他们*，让循环仍然是结构化的。捕获的输出回流给你。

构建正确的反馈循环，bug 就修好了 90%。

### 收紧循环

把循环当产品对待。一旦有了*一个*循环，就**收紧**它：

- 能让它更快吗？（缓存 setup、跳过无关初始化、收窄测试范围。）
- 能让信号更锐利吗？（断言具体症状，而不是「没崩溃」。）
- 能让它更确定吗？（钉住时间、给 RNG 播种、隔离文件系统、冻结网络。）

一个 30 秒且 flaky 的循环比没有循环好不了多少；一个 2 秒且确定性的循环才是紧凑的——是调试超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。把触发循环 100 次、并行化、加压力、收窄时间窗口、注入 sleep。50% 概率 flake 的 bug 是可调试的；1% 的不是——持续提升复现率，直到可调试为止。

### 当你真的建不出循环时

停下来，明确说出来。列出你试过什么。向用户请求：(a) 能复现它的环境的访问权，(b) 脱敏后的捕获工件（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 添加临时生产插桩的许可。**不要**在没有循环的情况下进入假设阶段。

### 完成标准——一个能变红的紧凑循环

当循环**紧凑**且**能变红（red-capable）**时，阶段 1 才算完成：你能说出**一条命令**——脚本路径、测试调用、curl——你**已经至少跑过一次**（展示调用及其脱敏后的输出），并且它：

- [ ] **能变红** — 它驱动真实的 bug 代码路径，并断言**用户描述的确切症状**，所以它能在该 bug 上变红、修复后变绿。不是「跑完没报错」——它必须能*抓住这个特定的 bug*。
- [ ] **确定性** — 每次运行判定相同（flaky bug：按上文，钉住并保持高复现率）。
- [ ] **快** — 以秒计，不以分钟计。
- [ ] **agent 可运行** — 你可以无人值守地运行它；只通过 `scripts/hitl-loop.template.sh` 让人类进环。

如果你发现自己在该命令存在之前就读代码构建理论，**停下——直接跳到假设正是本 skill 要防止的失败。** 没有能变红的命令，就没有阶段 2。

## 阶段 2 — 复现 + 最小化

运行循环。看着它变红——bug 出现了。

确认：

- [ ] 循环产生的是**用户**描述的失败模式——不是碰巧在附近的另一种失败。修错 bug = 修错方向。
- [ ] 失败可跨多次运行复现（或对非确定性 bug，复现率高到足以对着它调试）。
- [ ] 你已捕获确切症状（错误信息、错误输出、缓慢的耗时），以便后续阶段验证修复确实对症。

### 最小化

变红之后，把复现收缩到**仍然变红的最小场景**。**一次一个**地砍掉输入、调用方、配置、数据和步骤——每砍一刀重跑一次循环——只保留对失败起承重作用的部分。

为什么要费这个劲：最小复现会收缩阶段 3 的假设空间（剩下的可疑活动部件更少），并成为阶段 5 干净的回归测试。

完成标准是**剩下的每个元素都承重**——移除其中任何一个，循环就变绿。

在复现**并且**最小化之前，不要继续。

### 模式分析

复现后、假设前，与可正常工作的代码对比：

- 在同一代码库中找类似的正常代码，完整阅读参考实现——不略读。
- 列出正常代码与出错代码之间的**每一个**差异，无论多小——不要假设"那不可能有影响"。
- 差异往往就是根因所在。

## 阶段 3 — 提出假设

在检验任何假设之前，先生成 **3–5 个排好序的假设**。只生成单个假设会让你锚定在第一个看似合理的想法上。

每个假设必须**可证伪**：说出它做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更严重。"

如果你说不出预测，这个假设就是一团感觉——丢弃它或磨利它。

**在检验之前，把排好序的列表展示给用户。** 他们往往拥有能瞬间重排的领域知识（「我们刚部署了改动 #3」），或知道已经排除过的假设。便宜的检查点，省下大量时间。但不要被它阻塞——如果用户 AFK，就按你的排序继续。

### 单因素排除法

当有多个候选原因（多个功能/模块/流程步骤）时：列出全部候选，逐条做减法——去掉某个因素后问题不再出现，那个因素就是根因。一次只排除一个。

## 阶段 4 — 插桩

每个探针都必须对应阶段 3 的一个具体预测。**一次只改一个变量。**

工具偏好：

1. **调试器 / REPL 检查**，如果环境支持。一个断点胜过十条日志。
2. **定点日志**，打在能区分假设的边界上。
3. 永远不要「什么都记，然后 grep」。

**给每条调试日志打标签**，用唯一前缀，如 `[DEBUG-a4f2]`。收尾清理就变成一次 grep。没标签的日志会活下来；有标签的会被清除。

**多组件系统**（CI → 构建 → 签名，API → 服务 → 数据库）：先收集跨组件边界证据。在**每个组件边界**记录进入和离开的数据、验证环境/配置的传递、检查每层状态。执行一次以确定断裂点在哪一层，再针对该组件深入。

**性能分支。** 对性能回归，日志通常是错的工具。改为：先建立基线测量（计时 harness、`performance.now()`、profiler、查询计划），然后二分。先测量，后修复。

## 阶段 5 — 修复 + 回归测试

在修复**之前**写回归测试——但前提是存在一个**正确的 seam**。

正确的 seam 是测试能以调用点处真实发生的方式驱动**真实 bug 模式**的地方。如果唯一可用的 seam 太浅（bug 需要多个调用方却只能做单调用方测试、单元测试无法复现触发 bug 的链条），在那里写回归测试只会带来虚假的信心。

**如果不存在正确的 seam，这本身就是发现。** 记下来。是代码库架构在阻止这个 bug 被锁定。把它标记给下一个阶段。

如果存在正确的 seam：

1. 把最小化复现变成该 seam 处的一个失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 针对原始（未最小化的）场景重跑阶段 1 的反馈循环。

## 阶段 5b — 修复失败熔断

如果连续 3 次以上修复都失败，且每次修复都在别处暴露新的共享状态/耦合问题、或修复需要大规模重构——停下，这不是假设失败，是**架构问题**。在质疑根本架构并与人讨论之前，禁止第 4 次修复。模式是"惯性驱动下坚持了错误方案"的信号。

## 阶段 6 — 清理 + 事后复盘

宣布完成之前必须做到：

- [ ] 原始复现不再复现（重跑阶段 1 的循环）
- [ ] 回归测试通过（或已记录 seam 缺失）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 前缀）
- [ ] 一次性原型已删除（或移到明确标记的调试位置）
- [ ] 被证明正确的那个假设已写进 commit / PR 信息——让下一个调试者学到东西

**然后问：什么本可以阻止这个 bug？** 如果答案涉及架构变更（没有好的测试 seam、调用方纠缠、隐藏的耦合），带着具体细节交接给 `/improve-codebase-architecture` skill。建议要在修复落地**之后**提，而不是之前——现在你掌握的信息比开始时多。
