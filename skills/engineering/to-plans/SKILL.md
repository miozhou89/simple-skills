# 编写计划

**开始时宣布：** "我正在使用 to-plans 技能创建实现计划。"

**计划保存位置：** `docs/changes/<capability-path>/plans.md`。ship 流程中沿用已创建的变更目录；否则按变更命名并创建。用户偏好优先。

读者是对本代码库零上下文、不熟悉工具链与问题领域的工程师。计划要让他们知道：每个任务改哪些文件、要实现的接口与行为、需要查阅的文档、测试哪些场景、如何验证。将整个计划拆成小步骤任务，频繁 commit。

## 计划写什么，不写什么

计划描述**做什么、在哪做、如何验证**，不描述**怎么写成代码**。

- 写：文件路径；接口、类型、函数的名字与签名；用文字描述的字段与数据形状；行为、输入输出与约束；测试场景与期望结果；验证命令。
- 不写：函数体、结构体/类定义、测试代码、逐行实现步骤，或任何成段的代码块。

需要代码才能说清的决策属于实现阶段：在计划中写明要验证的行为，把写法留给 implement / tdd。

## 范围检查

规格若涵盖多个独立子系统，建议拆分为独立计划——每个子系统一个。每个计划必须能独立产出可工作、可测试的软件。

## 文件结构

定义任务之前，先列出将创建或修改的文件及各自职责——这是锁定分解决策的地方，它决定任务分解：

- 按职责拆分，而非按技术层级拆分；一起变更的文件放在一起。
- 在现有代码库中遵循已有模式，禁止单方面重构；仅当要修改的文件已难以管理时，才把拆分纳入计划。

每个任务应产出独立的、有意义的变更。

## 任务粒度定界

一个任务是**能独立承载自己那一轮测试循环、且值得一个全新审查者把关**的最小单元。划任务边界时：把搭建、配置、脚手架和文档这些步骤，折进那个真正需要它们的交付物所在的任务里；只在「审查者有可能否掉这个任务、同时批准它旁边那个」的地方才拆开。每个任务都以一个**可独立测试的交付物**结束。

**每步是一个可验证的操作（2-5 分钟）：** 写测试场景 → 运行确认失败 → 实现到通过 → 运行确认 → commit。步骤写清做什么、在哪个文件、验收什么，不贴代码。

## 计划文档头部

**每个计划必须以此头部开始：**

```markdown
# [功能名称] 实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 implement skill 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。

**目标：** [一句话描述要构建什么]

**架构：** [2-3 句话描述方案]

**技术栈：** [关键技术/库]

---
```

## 任务结构

- 一个目标拆分成多个相对独立的任务，任务应该小、清晰、逻辑顺序合理。
- 每个任务以"任务 N"作为命名前缀；每个任务又分多个执行步骤，每个步骤以 "- [ ] N.x <步骤描述>" 来跟踪进度。
- 制定计划过程中要追问：最容易出问题的是哪一步，有没有考虑其他方案，这次改动可能破坏哪些已有功能。计划改到足够清楚以后再保存。
- 每个任务组自带其工作所需的测试和文档。

示例：

````markdown
### 任务 2：图层清理

- [ ] 2.1 新建测试 `tests/exact/path/to/test.cpp`，覆盖「清除存在的图层」「图层不存在时无操作」「清除后其它图层不变」，先确认失败。
- [ ] 2.2 修改 `exact/path/to/file.h`，声明 `clearLayers(std::string_view name)`：返回是否找到该图层，不改变其它图层。
- [ ] 2.3 修改 `exact/path/to/file.cpp`，实现 `clearLayers()`，让 2.1 全绿。
- [ ] 2.4 Commit：`feat: clear named layers`。

````

## 禁止占位符

每个步骤都必须具体到可执行：指明文件、行为、测试场景与期望结果。以下是**计划缺陷**——绝不要写出来：
- "待定"、"TODO"、"后续实现"、"补充细节"
- "添加适当的错误处理" / "添加验证" / "处理边界情况"
- "为上述功能写测试"（没有具体场景与期望结果）
- "类似任务 N"（工程师可能不按顺序阅读任务）
- "实现 X" 却不指明改哪个文件、什么行为、如何验证
- 引用了 spec、现有代码和本计划中都找不到的类型、函数或方法
- 函数体、类型定义、测试代码或大段代码块

## 自检

编写完整计划后，以全新视角审视规格并对照检查计划。这是你自己执行的检查清单——不是子代理调度。

**1. 规格覆盖度：** 浏览规格中的每个章节/需求。你能指出实现它的任务吗？列出所有遗漏。

**2. 占位符扫描：** 搜索计划中的红旗——上方"禁止占位符"章节中的任何模式。修复它们。

**3. 实现细节扫描：** 搜索代码围栏、函数体、类型定义和测试代码。发现即删除，改写成契约、行为或测试场景。

**4. 类型一致性：** 后续任务中提到的类型、方法签名和属性名，是否与 spec、现有代码或前面任务中已点名的接口一致？任务 3 中叫 `clearLayers()` 但任务 7 中叫 `clearFullLayers()` 就是 bug。

如果发现问题，直接内联修复。无需重新审查——修好继续推进。如果发现规格中的需求没有对应任务，就添加任务。

## 执行交接

保存计划后，提醒用户审批。在用户接受计划之前，禁止修改代码。

用户批准计划后，调用 implement skill 开始执行计划。
