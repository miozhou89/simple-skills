# 头脑风暴：将想法转化为设计

通过自然的协作对话，把想法打磨成完整的设计和规格说明。先了解项目上下文，再逐一提问完善想法；理解要构建的内容后展示设计方案，获得用户批准才进入实现。

<HARD-GATE>
在你展示设计方案并获得用户批准之前，禁止调用任何实现技能、编写代码、搭建项目或采取任何实现行动。这适用于所有项目，无论看起来多简单——一个待办列表、单函数工具、配置变更全都需要。"简单"的项目正是未经检验的假设造成最多浪费的地方。设计可以很简短（真正简单的项目几句话即可），但必须展示并获得批准。
</HARD-GATE>

## 检查清单

为以下每个条目创建任务，并按顺序完成：

1. **探索项目上下文** — 检查文件、文档、最近的 commit。
2. **提供视觉伴侣**（仅当主题涉及视觉问题）— 独立消息，不与澄清问题合并。见下方「视觉伴侣」。
3. **提出澄清问题** — 每次一个，重点理解目的、约束、成功标准。
   - 提问前先评估范围：若需求含多个独立子系统（如"聊天、文件存储、计费和分析平台"），立即指出，不要用问题细化一个需要先拆分的项目。
   - 项目过大、单个规格无法覆盖时，先拆成子项目：有哪些独立部分、彼此关系、构建顺序。每个子项目走各自的规格 → 计划 → 实现周期。
   - 范围适当时每次一个问题；一个主题需更多探索就拆成多个问题。尽量用选择题，开放式问题也可。
4. **提出 2-3 种方案** — 附权衡分析和推荐。以对话方式展示选项，先讲推荐方案及理由。严格遵循 YAGNI，移除每个方案和设计里的不必要功能。
5. **分节展示设计** — 涵盖架构、组件、数据流、错误处理、测试。每节篇幅匹配复杂度：简单几句话，复杂最多 200-300 字。每节展示后询问是否正确，随时回头澄清不明确之处。
6. **编写设计文档** — 保存到 `docs/specs/YYYY-MM-DD-<topic>-design.md` 并 commit（用户对位置的偏好优先于此默认值）。若可用，使用 elements-of-style:writing-clearly-and-concisely 技能。
7. **规格自检** — 编写后以全新视角审视：
   - **占位符扫描：** 有没有"待定"、TODO、未完成章节或模糊需求？修复。
   - **内部一致性：** 章节间有无矛盾？架构与功能描述匹配吗？
   - **范围检查：** 能否用一个实现计划覆盖，还是需要进一步拆分？
   - **模糊性检查：** 有没有可被两种方式理解的需求？有则选一种并明确写出。
   - 发现问题直接内联修复，无需重新审查。
8. **用户审查规格** — 请用户在继续前审查文件：
   > "规格已编写并 commit 到 `<path>`。请审查一下，如果在我们开始编写实现计划之前你想做任何修改，请告诉我。"
   - 等待回复。要求修改则做出修改并重跑规格自检，用户批准后才继续。
9. **过渡到实现** — 调用 writing-plans 技能创建实现计划。这是头脑风暴后唯一要调用的技能——不要调用 frontend-design、mcp-builder 或其他实现技能。

**面向隔离和清晰的设计**（贯穿步骤 1-5）：
- 将系统拆成更小的单元，每个单元职责明确、接口清晰、可独立理解和测试。
- 对每个单元应能回答：它做什么、如何使用、依赖什么？别人能否不看内部实现就理解它？你能否在不影响调用者的前提下改内部实现？不能则调整边界。
- 更小、边界清晰的单元更便于工作：一次能放入上下文的代码更好推理，文件越专注编辑越可靠。文件变大通常意味着职责过多。

**在现有代码库中工作**：
- 提出更改前先探索现有结构，遵循现有模式。
- 若现有代码有问题影响当前工作（文件过大、边界不清、职责纠缠），把针对性改进纳入设计——像优秀开发者在工作中改进经手的代码。
- 不提议无关重构，只做服务当前目标的事。

## 视觉伴侣

基于浏览器的伴侣工具，用于在头脑风暴中展示原型、图表和视觉选项。它是工具不是模式——接受它意味着问题适合视觉呈现，不意味着每个问题都要通过浏览器。

**提供伴侣：** 预计后续问题涉及视觉内容（原型、布局、图表）时，提出一次以获得同意：
> "我们接下来讨论的一些内容，如果能在浏览器中展示给你看可能会更直观。我可以在讨论过程中为你制作原型、图表、对比图和其他视觉材料。这个功能还比较新，可能会消耗较多 token。要试试吗？（需要打开一个本地 URL）"

**独立消息：** 此提议必须单独一条消息，不与澄清问题、上下文摘要或任何内容合并，消息中只含上述提议。等待回复；拒绝则继续纯文本头脑风暴。

**逐问题决策：** 即使用户接受，每个问题仍单独决定用浏览器还是终端。判断标准：**用户看到是否比读到更容易理解？**
- **浏览器**：展示本身就是视觉的内容——原型、线框图、布局对比、架构图、并排视觉设计
- **终端**：文本内容——需求问题、概念选择、权衡列表、A/B/C/D 文字选项、范围决策

UI 主题问题不一定是视觉问题。"在这个上下文中个性化是什么意思？"是概念问题（用终端）。"哪种向导布局更好？"是视觉问题（用浏览器）。

若用户同意使用伴侣，继续前阅读 `skills/engineering/brainstorming/visual-companion.md`。
