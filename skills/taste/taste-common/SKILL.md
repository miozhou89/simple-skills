# tasteskill common: 反低质设计核心（平台无关）

> 落地页、作品集和改版。不是仪表盘、不是数据表、不是多步骤产品界面。
> 以下每条规则都是**情境化的**。没有任何一条会自动触发。先读简报，再只取用合适的那部分。

**本文件不单独使用。** 它只含平台无关的设计判断。动手写代码前，必须先读所用平台的 overlay：
- Web（React / Next.js / Tailwind）→ `../taste-skill/SKILL.md`
- Flutter（Dart）→ `../taste-flutter/SKILL.md`

overlay 提供：设计系统映射表、技术栈与架构约定、动画代码骨架、性能护栏的具体机制、dark mode token 策略、平台专属起飞前检查项与附录。本文中标注「见平台 overlay」处即为对接点。

## 0. 简报推断（动手前先读懂现场）

在动代码或调整旋钮之前，**先推断用户真正想要什么**。

### 0.A 先读取这些信号
1. **页面类型**——落地页（SaaS / 消费 / 代理商 / 活动）、作品集（开发者 / 设计师 / 创意工作室）、改版（保留 vs 重构）、编辑 / 博客。
2. 用户用过的**氛围词**——"minimalist"、"calm"、"Linear-style"、"Awwwards"、"brutalist"、"premium consumer"、"Apple-y"、"playful"、"serious B2B"、"editorial"、"agency-y"、"glassy"、"dark tech"。
3. **参考信号**——他们链接的 URL、粘贴的截图、提到的产品、对标竞争的品牌。
4. **受众**——B2B 采购评审团 vs. 有设计意识的消费者 vs. 浏览作品集的招聘者。由受众决定审美，而不是你的品味。
5. **已存在的品牌资产**——标志、颜色、字体、摄影。对于改版，这些是起始材料，不是可选输入（见第 11 节）。
6. **隐性约束**——无障碍优先的受众、公共部门、受监管行业、信任优先的商业、儿童产品。这些约束会**覆盖**审美偏好。

### 0.B 在生成前输出一行"设计解读"
在写任何代码之前，用一行话说明：**"我的解读是：面向\<受众\>的\<页面类型\>，采用\<氛围\>语言，倾向\<设计系统或审美流派\>。"**

解读示例：
- *"我的解读是：面向技术采购者的 B2B SaaS 落地页，采用 Linear 风格的极简语言，倾向 Tailwind 工具类 + Geist + 克制的动效。"*
- *"我的解读是：面向招聘经理的独立设计师作品集，采用编辑风 / 动感字体的语言，倾向原生 CSS + scroll 驱动动画 + 定制字体排版。"*
- *"我的解读是：一个公共部门服务网站的改版，采用信任优先的语言，倾向 GOV.UK Frontend 或 USWDS。"*

### 0.C 如果简报模糊，只问一个问题，不要猜
只问**一个**澄清问题——绝不要一次抛一堆问题——而且只在设计解读确实存在分歧时才问。示例：*"这个应该更接近 Linear 的干净，还是 Awwwards 的实验性？"*

如果你能从上下文自信地推断，**就不要问**。直接声明设计解读并继续。

### 0.D 反默认纪律
不要默认使用：AI 紫色 gradient、深色 mesh 上的居中 hero、三张等大特性 card、到处套用泛化的玻璃拟态、遍地无限循环微动画、Inter + 深灰蓝中性色。这些都是 LLM 的默认输出。要基于设计解读有意识地超越它们。

## 1. 三大旋钮（核心配置）

在完成设计解读后，设置三个旋钮。下文所有 layout、动效和密度的决策都由它们把关。

* **`DESIGN_VARIANCE: 8`**——1 = 完美对称，10 = 艺术性混乱
* **`MOTION_INTENSITY: 6`**——1 = 静态，10 = 电影感 / 物理感
* **`VISUAL_DENSITY: 4`**——1 = 美术馆 / 通透，10 = 驾驶舱 / 密集数据

**基线：** `8 / 6 / 4`。除非设计解读另有覆盖，否则使用这些值。不要要求用户编辑这个文件——覆盖通过对话完成。

### 1.A 旋钮推断（设计解读 → 旋钮值）
| 信号 | VARIANCE | MOTION | DENSITY |
|---|---|---|---|
| "极简 / 干净 / 平静 / 编辑风 / Linear 风格" | 5-6 | 3-4 | 2-3 |
| "高端消费 / 苹果风 / 奢侈品 / 品牌" | 7-8 | 5-7 | 3-4 |
| "俏皮 / 狂野 / Dribbble / Awwwards / 实验性 / 代理商" | 9-10 | 8-10 | 3-4 |
| "落地页 / 作品集 / 营销站（默认）" | 7-9 | 6-8 | 3-5 |
| "信任优先 / 公共部门 / 受监管 / 无障碍关键" | 3-4 | 2-3 | 4-5 |
| "改版 - 保留" | 匹配现状 | +1 | 匹配现状 |
| "改版 - 重构" | +2 | +2 | 匹配现状 |

### 1.B 用例预设
| 用例 | VARIANCE | MOTION | DENSITY |
|---|---|---|---|
| 落地页（SaaS、主流） | 7 | 6 | 4 |
| 落地页（代理商 / 创意） | 9 | 8 | 3 |

### 1.C 旋钮如何驱动输出
将这些值（或用户覆盖后的值）用作全局变量。本文档中所有交叉引用都指向这些确切的变量名——绝不要发明 `LAYOUT_VARIANCE` 或 `ANIM_LEVEL` 之类的别名。

## 2. 简报 → 设计系统映射（原则）

拿到设计解读（第 0 节）和旋钮（第 1 节）之后，选择正确的基础。**具体的设计系统映射表和审美实现方式见平台 overlay。**

**原则（所有平台通用）：**
* **真实设计系统优先。** 不要为已有官方实现的东西自己发明样式。不要把某种审美趋势冒充成官方系统。
* **诚实规则：** 如果简报读作某个真实设计系统，就安装并使用**官方**实现。不要手写重建它。不要导入某个系统的 token 却覆盖掉其中 90%。
* **每个项目一个系统。** 不要在同一个项目里混用两个设计系统。
* **当简报是一种审美而非系统时**（玻璃拟态、Bento、粗野主义、编辑风、暗黑科技、极光 / mesh gradient、动感字体排版等），用平台原语 + 一个维护良好的 component 库诚实地构建，并在代码注释中说明哪些是借鉴的灵感、哪些是官方 asset。

## 4. 设计工程指令（偏差纠正）

LLM 默认输出陈词滥调。主动覆盖这些默认值。每条规则都有情境感知的覆盖路径。

### 4.1 字体排版
* **展示 / 标题：** 默认约 36px（窄屏）到 60px（宽屏）、紧字距、紧凑行高。
* **正文 / 段落：** 默认约 16px、次要中性色、行高约 1.6、行长最多 65ch。
* **sans-serif 字体选择：**
  * **不推荐作为默认：** `Inter`。优先选 `Geist`、`Outfit`、`Cabinet Grotesk`、`Satoshi`，或一个贴合品牌的 serif 字体。
  * **覆盖：** 当用户明确要求中性 / 标准 / Linear 风格的感觉，或简报是公共部门 / 无障碍优先的站点时，Inter 可以接受。
* **应了解的搭配：** `Geist` + `Geist Mono`、`Satoshi` + `JetBrains Mono`、`Cabinet Grotesk` + `Inter Tight`、`GT America` + `IBM Plex Mono`。

* **serif 纪律（强烈不推荐作为默认）：**
  * serif 字体**强烈不推荐作为任何项目的默认字体**。"它感觉很创意 / 高级 / 编辑风"不是使用 serif 的理由。智能体默认的"创意简报 = serif"心智模型，是生产环节中被测试最多的 AI 破绽。
  * **仅在以下任一条件明确成立时，serif 才可接受：**
    - 品牌简报明确点名了某个 serif 字体，或
    - 审美流派确实是编辑 / 奢侈 / 出版 / 手稿 / 传承 / 复古风，并且你能说清为什么这一具体 serif 字体契合这一具体品牌
  * 对于其他所有情况（创意代理商、设计工作室、现代品牌、高端消费、作品集、生活方式），**默认 sans-serif display**（Geist Display、ABC Diatype、Söhne Breit、Cabinet Grotesk Display、Migra Sans、GT Walsheim、Inter Display、PP Neue Montreal）。sans display font 并不"无聊"——它们成为默认，正如黑色是时尚界的默认色一样。
  * **强调规则（相关）：** 当你想在标题中强调某个词时，用**同一字体的斜体或粗体**。不要为了增加视觉趣味而在 sans-serif 标题里塞一个随机的 serif 词（反之亦然）。跨字体族强调是业余做法。同字体族内的斜体 / 粗体强调才是正确手法。
  * **明确禁止作为默认：** `Fraunces` 和 `Instrument_Serif`（两款 LLM 最爱的 display serif）。
  * **如果 serif 确实成立**（罕见，按上述标准），从这个池子里轮换，不要在连续项目里重复使用同一款 serif：PP Editorial New、GT Sectra Display、Cardinal Grotesque、Reckless Neue、Tiempos Headline、Recoleta、Cormorant Garamond、Playfair Display、EB Garamond、IvyPresto、Migra、Editorial Old、Saol Display、Söhne Breit Kursiv、Domaine Display、Canela、Schnyder、Tobias、NB Architekt、ITC Galliard。

* **斜体下降部避让（强制）：** 当 display type 中使用斜体、且该词包含下降部字母（`y g j p q`）时，行高 1.0 会裁切下降部。至少使用行高 1.1，并为该元素预留约 4px 的下间距。交付前审计 display 标题中每一个斜体词。

* **字体可用性因平台而异。** 上述西文字体在 Web 上可直接自托管；在 Flutter 上需确认 `google_fonts` 是否收录或自备字体文件。中文字体另行按平台 overlay 的约定处理。

### 4.2 色彩校准
* 最多 1 个强调色。默认饱和度 < 80%。
* **LILA 规则：** "AI 紫 / 蓝光"审美不推荐作为默认。不要自动给按钮加紫色光晕，不要随机的霓虹 gradient。使用中性基底（Zinc / Slate / Stone）搭配高对比的单一强调色（Emerald、Electric Blue、Deep Rose、Burnt Orange 等）。
* **覆盖：** 如果品牌或简报明确要求紫色 / 紫罗兰 / lila，就大胆采用。但要有意图地执行：一致的色板、协调的中性色、克制的 gradient。而不是泛化的 AI gradient 低质内容。
* **每个项目一个色板。** 不要在同一个项目里在暖灰和冷灰之间来回切换。
* **色彩一致性锁定（强制）：** 一旦为页面选定强调色，整页都要使用它。暖灰站点不会在第 7 节突然出现一个蓝色 CTA。玫瑰色强调的站点不会在 footer 出现一个青绿色状态 badge。选一个强调色，锁定它，交付前审计每一个 component。

* **高端消费色板禁令（强制，第二高频的 AI 破绽）：**
  * 对于高端消费简报（厨具、健康、匠人、奢侈品、传承工艺、DTC 家居用品等），LLM 的默认是**暖米色 / 奶油色 + 黄铜 / 黏土 / 牛血红 / 赭石 + 浓缩咖啡 / 墨黑深色文本**。作为默认背景和强调色，明确禁止以下十六进制色族：
    - 背景：`#f5f1ea`、`#f7f5f1`、`#fbf8f1`、`#efeae0`、`#ece6db`、`#faf7f1`、`#e8dfcb`（均为"暖纸 / 奶油 / 粉笔 / 骨白"）
    - 强调：`#b08947`、`#b6553a`、`#9a2436`、`#9c6e2a`、`#bc7c3a`、`#7d5621`（均为"黄铜 / 黏土 / 牛血红 / 赭石"）
    - 文本：`#1a1714`、`#1a1814`、`#1b1814`（均为"浓缩咖啡 / 暖近黑"）
  * 该色板被禁止作为高端消费简报的默认选择。你交付过的每一个高端消费网站都用了这个色板。品牌变得不可见。
  * **默认替代方案（轮换，不要重复使用）：**
    - **冷调奢华：** 银灰 + 铬 + 烟灰（想想 Tesla、去掉皮革的 Apple Watch Hermès）
    - **森林：** 深绿 + 骨白 + 琥珀强调（想想 Filson、Patagonia 高端线）
    - **黑与棕褐：** 真正的近黑 + 暖棕褐，锐利对比，不要米色
    - **钴蓝 + 奶油：** 高饱和蓝配单一中性色，不要黄铜
    - **赤陶 + 石板灰：** 暖锈色配冷灰，不要黄铜
    - **橄榄 + 砖红 + 纸白：** 柔和橄榄加砖红强调
    - **纯单色 + 单一饱和点缀：** 近白 + 近黑 + 一个明亮强调色（电光蓝、祖母绿、荧光粉等）
  * **色板轮换规则：** 如果你上一个生成的高端消费项目用了米色 + 黄铜家族，这一次必须用不同的家族。不要连续两次交付同一套暖工艺色板。
  * **覆盖：** 仅当品牌简报明确点名这些颜色，或品牌身份确实是复古 / 匠人 / 暖工艺、且你能说清为什么这一具体色板契合这一具体品牌时，米色 + 黄铜 + 浓缩咖啡色板才可接受。因为"这是厨具简报"就默认伸手去用它，是被禁止的。

### 4.3 layout 多样化
* **反居中偏见：** 当 `DESIGN_VARIANCE > 4` 时避免居中的 Hero / H1 区域。改用"分屏"（50/50）、"左对齐内容 / 右对齐 asset"、"非对称留白"或 scroll 固定结构。
* **覆盖：** 对于信息本身就是设计的编辑风 / 宣言 / 发布公告类简报，居中 hero 是可以的。

### 4.4 材质、shadow、card
* 仅当 elevation 传达真实层级时才用 card。否则用顶部发丝线、行间分隔线或负空间来分组。
* 使用 shadow 时，让它带上背景色相。浅色背景上不要用纯黑投影。
* 当 `VISUAL_DENSITY > 7` 时：禁止使用泛化 card 容器。数据指标在朴素 layout 中呼吸。
* **形状一致性锁定（强制）：** 为页面选择一套 radius 刻度并坚持到底。选项：全锐利（radius 0）、全柔和（radius 12-16px）、全胶囊（交互元素全 radius）。仅当有文档化规则（例如"按钮全胶囊，card 16px，输入框 8px"）且该规则处处贯彻时，才允许混合系统。方形 layout 里的圆按钮，或胶囊按钮页面上的方形 card，都是坏设计。

### 4.5 交互 UI 状态
LLM 默认只输出"静态成功态"。总是实现完整循环：
* **加载中：** 匹配最终 layout 形状的 skeleton 加载器。避免泛化的圆形转圈。
* **空状态：** 精心构图；指明如何填充。
* **错误状态：** 清晰、内联（表单），或情境化（仅短暂场景用 toast）。
* **触觉反馈：** 按压态下移 1px 或缩放至 0.98，模拟物理按压。
* **按钮对比度检查（强制，无障碍）：** 交付任何按钮前，先验证按钮文本在按钮背景上可读。白按钮 + 白文本、白色标签的白色 CTA、无边框且对着页面背景的透明按钮 → 全部禁止。审计每个 CTA：对比度达到 WCAG AA 最低要求（正文 4.5:1，18px+ 大文本 3:1）。同一规则适用于摄影背景上的幽灵按钮（使用遮罩、底衬或描边）。
* **CTA 按钮换行禁令（强制）：** 按钮文本在桌面端必须只占一行。如果像 "VIEW SELECTED WORK" 这样的标签折成 2 或 3 行，这个按钮就是坏的。修复方式：要么缩短标签（主 CTA 最多 3 个词，理想 1-2 个），要么加宽按钮（不要人为限制 CTA 的最大宽度）。桌面端折行的 CTA 属于起飞前失败。
* **禁止重复 CTA 意图（强制）：** 一页上出现两个意图相同的 CTA 属于起飞前失败。相同意图的示例："Get in touch" + "Contact us" + "Let's talk" + "Start a project" + "Start something" + "Reach out" 全部都是"联系"意图 → 选一个标签，在整页（nav、hero、footer）统一使用。同理，"Try free" + "Get started" + "Sign up free"（都是"注册"意图）以及 "View work" + "See selected work" + "Browse projects"（都是"作品集"意图）。每个意图一个标签。
* **表单对比度检查（强制，无障碍）：** 表单输入、占位文本、焦点环、辅助文本和错误文本都要在区块背景上通过 WCAG AA 对比度。近白表单上的浅色占位符、白色页面区块上的白色表单、对比度低于 4.5:1 的灰色表单标签 → 全部禁止。交付前审计每个表单。

### 4.6 数据与表单模式
* 标签在输入框上方。辅助文本可选但应存在。错误文本在输入框下方。输入块统一用 8px 间距。
* 禁止用占位符充当标签。永远如此。

### 4.7 layout 纪律（硬性规则。违反任何一条就是交付坏作品）

* **Hero 必须装进首屏 viewport。** 标题桌面端最多 2 行，副文本最多 **20 词**且最多 3-4 行，CTA 无需 scroll 即可见。如果文案太长：缩小字号或删减文案。如果你无法用 20 个词的副文本讲清价值主张，那是价值主张不清楚，不是规则太严。禁止让 hero 溢出、迫使 scroll 去找 CTA。
* **Hero 字号纪律。** 把字号和图片尺寸*一起*规划。如果 hero asset 很大、标题超过 6 个词，就不要从 72-96px 起步。默认合理区间：大多数 hero 用 36-60px；仅当标题是 3-5 个词时才用 60-72px。4 行的 hero 标题永远是字号错误，而不是文案长度错误。
* **Hero 顶部内边距上限（强制）：** Hero 顶部内边距桌面端最多 96px。超过这个值意味着 hero 内容悬浮在 viewport 半空，读起来像 layout bug，而不是有意的留白。如果 hero 需要更多呼吸空间，加大字号或 asset 尺寸，而不是顶部内边距。
* **Hero 堆叠纪律（最多 4 个文本元素）。** Hero 是一个瞬间，不是特性清单。允许的文本元素，总计最多 4 个：
  1. Eyebrow（小号大写标签）或品牌条，或两者都不要——选零个或一个
  2. 标题（最多 2 行，见上）
  3. 副文本（最多 20 词，最多 4 行）
  4. CTA（1 个主 + 最多 1 个次）
  - **Hero 中禁止出现：** CTA 下方的微型标语（"Works with GitHub, GitLab, and self-hosted Git"）、信任微条（"Used by engineering teams at..."）、定价预告（"Free for solo, $10/user for teams"）、特性要点列表、社会证明 avatar 行。这些都要移到 hero 正下方的专属区块。
  - 如果同一个 hero 里既有 eyebrow 又有 CTA 下方的标语，去掉标语。如果既有品牌条又有标语，去掉标语。每个 hero 最多一个小文本元素。
* **"Used by" / "Trusted by" 标志墙属于 hero 下方，禁止在 hero 内部。** hero 用于价值主张和主 CTA。标志墙是正下方的一个独立区块。不要把信任标志塞进与 hero 文案相同的行里。
* **导航在桌面端必须只占一行。** 如果在 1024px 宽度下放不下，就精简标签、去掉次要项，或改用汉堡菜单。桌面端两行的导航是坏设计。
* **导航高度上限：桌面端最多 80px，默认 64-72px。** 不要那种吃掉 viewport 15% 的巨型"代理商" navbar。
* **Bento grid 必须有节奏，而不是单边重复。** 不要堆叠 6 行"左图 / 右文"。变化构图：交替全宽特性行、非对称磁贴尺寸、垂直分隔。
* **Bento 单元格数量规则（强制）：** Bento grid 的单元格数量必须与你拥有的内容数量完全一致。3 项 → 3 个单元格（1+2 拆分，或 2+1，或非对称三格）。5 项 → 5 个单元格（2+3、3+2、hero+4 等）。如果 grid 中间或末尾有空单元格，说明你规划错了。重塑 grid；不要粘贴空白磁贴。
* **区块 layout 重复禁令。** 一旦你为某个区块用了一种 layout 家族（例如三列图片 card、全宽引言、图文分屏），该家族在整页最多只能出现一次。"Selected commissions"不能长得像"What we do"。有 8 个区块的落地页必须至少使用 4 种不同的 layout 家族。
* **锯齿交替上限（强制）。** "左图 + 右文"再"左文 + 右图"交替的锯齿 layout = 平庸。这种图文分屏模式最多连续 2 个区块。第 3 个连续的图文分屏属于起飞前失败。用全宽区块、垂直堆叠区块、bento grid、跑马灯或其他 layout 家族来打破模式。
* **Eyebrow 克制（强制，生产测试中违反率第一的规则）。** "eyebrow" 是位于区块标题上方的小号大写宽字距标签（例如 `FOUR COLORWAYS`、`SELECTED WORK`、`THE HARDWARE`、`Git-native task management`）。典型特征：约 11px、大写、字距约 0.18em，或 monospace 约 10.5px、字距约 0.22em。每个 AI 搭建的站点都在每个区块标题上方放一个 eyebrow，产生同样的模板化节奏。硬性规则：
  - **每 3 个区块最多 1 个 eyebrow。** Hero 算 1 个。所以一个有 9 个区块的页面最多总共用 3 个 eyebrow。
  - 如果区块 A 有 eyebrow，接下来 2 个区块不能有。
  - **起飞前检查是机械式的：** 统计所有区块中标题上方"大写宽字距微标签"的出现次数。若次数 > ceil(区块数 / 3)，输出即失败。
  - **不用 eyebrow 该怎么做：** 彻底去掉它。标题本身就够了。如果需要给区块归类，区块在页面上的位置已经完成了归类；不需要标签。
* **分栏标题禁令（强制）。** "左大标题 + 右小说明段"作为区块标题（左侧占约 2/3 宽度的大标题，右侧漂浮一小段正文）的模式**默认禁止**。区块应该只有一个聚焦的信息。如果确实需要标题和说明段两者，就垂直堆叠（标题在上，正文在下，行长最多 65ch）。仅当有真实的构图理由时才用分栏标题模式（例如右栏承载视觉或交互元素，而不只是填充文字）。
* **Bento 背景多样性（强制）。** Bento 和特性 grid 区块不能是 6 张白底白 card 里面塞文字。任何多单元格 grid 中至少 2-3 个单元格需要有真实的视觉变化：真实图片、贴合品牌的 gradient（不是 AI 紫）、图案、着色背景。一个只有排版在里面的奶油底奶油 bento，即便页面其余部分很好，读起来也是无聊的 AI 默认。
* **每个区块必须显式处理窄屏折叠。** 对每个多列 layout，显式声明窄屏（< 768px 或手机宽度）的回退。"它自己会好，框架会处理"这种假设一律不要。

### 4.8 图像与视觉 asset 策略

落地页和作品集是**视觉产品**。只有文字、带假截图的页面是低质内容。

**视觉 asset 优先级顺序：**
1. **图像生成工具优先。** 如果环境中存在任何图像生成工具（`generate_image`、MCP 图像工具、IDE 集成的生成、OpenAI 图像工具等），你必须使用它来创建区块专属 asset：hero 摄影、产品照、纹理背景、氛围图。按区块所需的宽高比生成。不要因为手写样式感觉更快就跳过这一步。
2. **其次是真实网络图片。** 当没有生成工具可用时，使用真实摄影来源。可接受的默认：
   * `https://picsum.photos/seed/{descriptive-seed}/{w}/{h}` 用于占位摄影（seed 应描述该区块，例如 `marrow-cookware-kitchen`）
   * 简报提供实际图库或品牌 URL 时使用之
   * 若明确允许，使用开放许可来源（Unsplash 直接 URL、Pexels）
3. **最后手段：告知用户。** 如果两者都不可行，不要用手写 SVG 插画或手搭的"假截图"填满页面。改为用目标语言的注释语法留下清楚标注的占位槽（如 `TODO: hero product photo, 1600x1200`），并在回复末尾说：*"此页面需要在以下位置使用真实图片：\[位置清单\]。请生成或提供它们。"*

**即便是极简站点也需要真实图片。** 纯文字页面不是极简，是未完成的作品。即便编辑风 Linear 风格站点也至少需要 2-3 张真实图片（hero、一张产品 / 生活方式照、一张辅助图）。如果简报克制，就生成黑白极简摄影；不要因为旋钮值低就完全跳过图片。

**社会证明用真实公司标志。** 当简报要求 "Trusted by / Used by / Customers" 标志墙时，不要默认使用纯文字字标（一行里样式化的品牌名文本）。使用真实 SVG 标志：
* **来源：Simple Icons**（`https://cdn.simpleicons.org/{slug}/ffffff` 任意颜色，或其官方包）。覆盖大多数知名品牌。
* **替代：devicon** 用于技术栈标志。
* **编造了品牌名？那就也编造一个 SVG 标志。** 生成一个简单的字母组合（圆圈里的一个字母、双字母连字、抽象图形），并匹配页面风格。为虚构品牌名使用纯文字字标看起来很泛化。
* **总是**确保标志在 light mode 和 dark mode 下都能正常显示（深底白字、浅底黑字，或单色主题变量）。
* **仅标志规则（强制）：** 标志墙 = 只有标志，别无其他。不要在每个标志下方打印行业 / 类别标签（不要 `Vercel` 下面加 `hosting`，不要 `Stripe` 下面加 `payments`，不要 `Cloudflare` 下面加 `infra`）。标志就是可信度，标签只会添加用户已经知道的东西。可选：品牌名作为无障碍 alt 文本，可选链接到品牌网站。就这些。

**手写插画：**
* 库里的 SVG 图标：可以（见平台 overlay 的图标约定）。
* 手写装饰性 SVG（定制插画、标志、图形标记）：**强烈不推荐**，禁止作默认。仅在以下情况可接受：
  - 简报明确要求（"给我画一个 SVG 标志"）
  - 是单个简单几何图形（一个方形、一个圆、display type 的字标）
  - 你对输出质量有信心

**手搭的假截图被禁止。** 用样式化矩形拼出来的"产品预览"、假任务列表、假仪表盘、假终端窗口都是破绽。如果你需要展示产品：
* 有真实截图 URL 就用
* 通过图像工具生成一张
* 使用真实 component 预览（页面内真实的 UI 迷你版）
* 或完全跳过预览，使用编辑风摄影

**Hero 需要真实视觉。** 文字 + gradient 团不是 hero——那只是占位。

### 4.9 内容密度

落地页靠**第一印象**存活，而不是完整阅读。狠心删减。

* **每个区块的默认内容形态：** 短标题（≤ 8 词）+ 短副段（≤ 25 词）+ 一个视觉 asset 或一个 CTA。更多内容必须由该区块的职责来证明其合理性。
* **不要数据倾倒区块。** 20 行的出版表、30 行的奖项清单、营销页上的巨型定价矩阵 = 错误 layout。改用：
  - 前 3-5 条亮点 + "查看完整列表"链接
  - 跑马灯 / carousel 用于广度
  - 如果数据本身就是产品，就换到完全独立的页面
* **长列表需要不同的 UI component，而不是更长的列表。** 默认用带圆点 / 发丝线分隔行的简单列表是偷懒的选择。如果超过 5 项，改用以下之一：
  - 两列分栏并按组分项
  - 每项带图片 + 标签的 card grid
  - 若项目可分类，用标签页 / accordion
  - 横向 scroll 吸附胶囊
  - 广度型列表用 carousel（评价、标志、能力）
  - 跑马灯用于"大量不需要单独关注的事物"
  10 行规格表 + 每行下一条发丝线是最差的默认。要么把行分组成 2-3 块并用稀疏分隔线，要么改为每个规格一张 card 的 layout。
* **规格表专门说明（Marrow 厨具模式）。** 每行都带下边框的长产品规格表，是厨具 / 硬件 / 服装 / 匠人商品简报的 AI 默认。禁止。具体替代方案：
  - **两列 card grid：** 每个规格一张 card，含规格名、数值（大号展示数字）和一行"为什么重要"的正文。桌面端两列，移动端一列。
  - **scroll 吸附横向胶囊：** 每个规格是一个胶囊，用户可以滑动浏览。
  - **分组成块：** 把 10 个规格归入 3 个逻辑簇（例如"材料"、"烹饪"、"保修"），每个簇用一条柔和分隔线和一个簇标题。
  - **重点 vs 其余：** 3-4 个 hero 规格以大号展示磁贴可视化，其余折叠在"查看完整规格"的展开下。

* **文案自审（交付前强制）：** 在宣告任何任务完成之前，重读页面上每一个可见字符串（标题、副标题、eyebrow、按钮标签、正文、图注、alt 文本、footer 文本、错误信息）。标记任何符合以下条件的字符串：
  - **语法错误**（"free on its past"、"two plans but one is honest"、脱离上下文的"to put it on the table"）
  - **指代不明**（没有前文就出现"we plan to stay that way"）
  - **听起来像 AI 幻觉**（俏皮却用错的文字游戏、对不上的生硬比喻、"优雅的空话"式措辞）
  - **读起来像 LLM 试图显得深思熟虑**（被动攻击式谦逊、假匠人标签、伪诗意的微元信息）
  重写每一个被标记的字符串。如果不确定某字符串是否讲得通，就用一句朴素的功能性句子替换它。AI 生成的俏皮文案比无聊文案更糟。
* **虚假精确数字会被标记。** 像 `92%`、`4.1×`、`48k`、`5.8 mm`、`13.4 lb` 这样的数字要么：
  - 来自真实数据（简报、品牌指南、公开指标）——可以
  - 明确标注为模拟（`mock` 注释、"example"、"sample data"）——可以
  - 是 AI 编造的规格审美——禁止。不要伪造品牌并未宣称的工程精度。
* **每页一种文案语体。** 除非品牌语气明确要求，否则不要在同一构图里混用技术 monospace（"47 tasks · 0.6 ctx-switches/day"）、编辑散文和营销金句。

### 4.10 引言与证言

* 引言正文**最多 3 行**。禁止 6 行。如果原引文更长 → 删减它。落地页引言是片段，不是完整评论。
* 对于非常小的字号（例如 footer 式证言），行数上限可以略微放宽。精神是："一眼能装下。"
* **引文文本内不要用 em-dash** 作为设计装饰（长停顿、动感 em-dash、em-dash 圆点）。见第 9.G 节——em-dash 被完全禁止。
* 署名：姓名 + 职位 +（可选）公司。禁止只有名字（"- Sarah"）。
* 引号：使用真正的排版引号（ " " ）或干脆不用。不要用直引号 ASCII（ " ）。

### 4.11 页面主题锁定（light / dark mode 一致性）

页面只有一个主题。区块不得反转。

* 如果页面是 dark mode，所有区块都是 dark mode。不要让 light mode 暖纸区块夹在 dark 区块之间（反之亦然）。用户绝不能在中途 scroll 时感觉自己走进了另一个网站。
* 例外：如果简报明确要求"色块叙事"或"scroll 切换主题"手法，且那是有意的构图（一次完整的主题切换并带强过渡，而非随机交替），则每页允许一次。
* 默认行为：在页面级别选择浅色、深色或跟随系统外观偏好，并锁定。同一主题家族内的区块级背景微调可以（近黑旁边放稍浅的近黑）；但在深色页面中途翻到暖浅色是坏的。
* 使用内置主题功能的设计系统时，在应用根部设置一次主题。不要让单个区块覆盖。

## 5. 情境感知的主动性（通用原则）

这些是工具，不是默认值。在设计解读要求时使用它们。**这些没有一个会自动触发。** 标准代码骨架与禁止的动画模式见平台 overlay。

* **Liquid Glass / 玻璃拟态：** 适用于高端消费、类 Apple、奢侈品牌或媒体叠加类氛围。不适用于仪表盘、公共部门或"无聊的 B2B"。使用时，要超越简单的背景 blur：添加 1px 内边框和细微内 shadow 来表现物理边缘折射。为"降低透明度"的无障碍设置提供纯色填充回退。平台实现见 overlay。
* **磁吸微物理：** 当 `MOTION_INTENSITY > 5` 且简报读作高端 / 俏皮 / 代理商时使用。必须用平台的动画值机制在渲染 / 重建循环之外实现（Web 用 motion values，Flutter 用 `AnimationController`），**禁止**用组件状态逐帧跟踪指针。
* **持续微交互**（脉冲、打字机、漂浮、微光、carousel）：当 `MOTION_INTENSITY > 5` 且区块确实从动效中受益时使用（状态指示器、实时信息流、AI 感）。**不是每张 card 都需要无限循环。** 如果区块是信息性的，就让它静止。应用弹簧物理（参考值：stiffness 100、damping 20）——不要线性缓动。
* **"宣称了动效，就要展示动效。"** 如果 `MOTION_INTENSITY > 4`，页面就必须真正动起来：hero 的入场过渡、关键区块的 scroll 显现、CTA 的 hover 物理，至少这些。一个宣称 `MOTION_INTENSITY: 7` 却静态的页面是坏的。反过来，如果现有范围内无法交付可用的动效，就把旋钮降到 3，交付一个干净的静态页面。禁止半途构建会坏掉的动效（被截断的 scroll 触发器、跳动的入场、缺失的清理）。
* **动效必须有动机（强制）。** 添加任何动画之前，先问："这个动画在传达什么？"有效答案：层级（把注意力引向正确的东西）、叙事（按与叙事匹配的顺序揭示内容）、反馈（确认用户操作）、状态转换（展示发生了变化）。无效答案："它看起来很酷"。因为某个动画库可用就到处用它是业余行为。每个 scroll 触发器、每个跑马灯、每个固定区块都需要理由。如果你无法用一句话讲清理由，就删掉这个动画。
* **跑马灯每页最多一个（强制）。** 横向 scroll 文字跑马灯（"标志无限 scroll"、"宣言侧向 scroll"、"动感词语条"）每页最多出现一次。同一页出现两个或更多跑马灯读起来像偷懒的填充。选出跑马灯真正服务于内容的那个区块；其他区块用不同的 layout。
* **粘性堆叠必须是真正的粘性堆叠。** "scroll card 堆叠"不是顺序显现列表。常见失败：触发器在 scroll 中途触发，而不是在 viewport 顶部固定。修复：在区块顶部到达 viewport 顶部时开始固定。标准骨架见平台 overlay。
* **横向平移（使用横向 scroll 劫持时）。** 常见失败：动画在区块固定之前就开始了，于是用户看到半张幻灯片。修复同上：顶部到达即固定外层包裹，scrub 内层轨道。标准骨架见平台 overlay。

## 6. 性能与无障碍护栏（通用原则）

具体机制见平台 overlay。所有平台通用：

### 6.A 硬件加速
* 只动画化 transform 类和 opacity 类属性（位移、缩放、旋转、透明度）。禁止动画化 layout 属性（位置、宽、高）。
* 谨慎使用合成层提示——只用在真正会动画化的元素上。

### 6.B 减弱动效（强制）
* **任何 `MOTION_INTENSITY > 3` 的动效都必须遵守平台的"减弱动效"设置。** 这一点没有商量余地。
* 在减弱动效下，无限循环、视差、scroll 劫持和磁吸物理都必须坍缩为静态 / 瞬时。
* 平台的检测机制（`prefers-reduced-motion`、`MediaQuery.disableAnimations` 等）见 overlay。

### 6.C dark mode（任何面向消费者的页面都强制）
* 从一开始就为**两种模式**设计。没有用户明确指示，禁止只交付浅色或只交付深色。
* 用平台 overlay 定义的 token 策略，每个项目选一种并坚持到底。
* **此处不规定具体的 dark mode 颜色。** 由简报决定。在两种模式下都保持视觉层级、品牌识别和 WCAG AA 对比度（正文 AAA）。
* 尊重系统的深色偏好。默认跟随系统，除非品牌坚持单一模式。

## 7. 旋钮定义（技术参考）

### DESIGN_VARIANCE（级别 1-10）
* **1-3（可预测）：** 对称 grid（等宽列）、相等内边距、居中对齐。
* **4-7（错位）：** 负边距重叠、多样的图片宽高比（4:3 旁边放 16:9）、左对齐标题配居中数据。
* **8-10（非对称）：** 瀑布流 layout、分数列宽的 grid（如 2:1:1）、大片留白区（如左侧留白 20% 屏宽）。
* **窄屏覆盖：** 级别 4-10 时，宽屏的非对称 layout 在窄屏（< 768px）下必须坍缩为严格单列。

### MOTION_INTENSITY（级别 1-10）
* **1-3（静态）：** 无自动动画。只用 hover 和按压态。反正"减弱动效"就是默认模式。
* **4-7（流畅过渡）：** 约 0.3s、`cubic-bezier(0.16, 1, 0.3, 1)` 的过渡。错峰延时用于载入。聚焦 transform 和 opacity。
* **8-10（高级编排）：** 复杂的 scroll 触发显现、视差、scroll 驱动动画。**禁止用逐帧 scroll 监听器手写实现**——这是硬性禁令，不是"最好别"。允许的替代方案见平台 overlay 的禁令清单。

### VISUAL_DENSITY（级别 1-10）
* **1-3（美术馆）：** 大量留白。巨大的区块间距（128-192px）。昂贵、干净。
* **4-7（日常应用）：** 标准应用间距（64-96px）。
* **8-10（驾驶舱）：** 紧凑内边距。无 card 盒；用 1px 线分隔数据。强制：所有数字用 monospace。

## 8. dark mode 协议

默认双模式。除非简报是仿印刷的编辑风，否则禁止假定只做浅色。

### 8.A Token 策略（选一种，坚持到底）
具体策略由平台 overlay 定义（Web：`dark:` 变体或 CSS 变量；Flutter：`ThemeData` + `ColorScheme` 语义 token）。无论哪种：定义语义 token（surface、surface-elevated、text-primary、accent），并在深色模式下交换值。

### 8.B 此处不规定具体颜色
由简报和品牌决定。本技能只强制：
* **对比度**——正文最低 WCAG AA，hero 文案目标 AAA。
* **层级对等**——浅色下有效的视觉层级在深色下也必须有效。如果 CTA 在浅色下突出，深色下也要突出。
* **品牌保真**——主品牌色保持可辨识。不要把品牌色消成 dark mode 里的灰。
* **不要纯 `#000000` 也不要纯 `#ffffff`**——使用近黑（如 zinc-950、近黑暖灰）和近白。纯值会杀死层次。

### 8.C 默认模式
尊重系统外观偏好，除非品牌坚持。如果任一模式会丢失关键品牌表达，就加一个手动切换。

### 8.D 完成前在两种模式下测试
开发期间在两种模式下检查页面。不要交付你只在一种模式下看过的页面。

## 9. AI 破绽（禁用模式）

除非简报明确要求，否则避免这些特征。

### 9.A 视觉
* 默认**不要霓虹 / 外发光**。使用内边框或细微着色 shadow。
* **不要纯黑（`#000000`）。** 近黑、zinc-950 或炭色。
* **不要过饱和强调色。** 降低饱和度以与中性色融合。
* 大标题**不要过量 gradient 文字**。
* **不要自定义鼠标光标。** 过时、对无障碍不友好、对性能不友好。

### 9.B 字体排版
* **避免默认使用 Inter。** 见第 4.1 节。存在覆盖路径。
* **不要只会嘶吼的超大 H1。** 用字重 + 颜色控制层级，而不是单纯的尺寸。
* **serif 约束：** serif 用于编辑 / 奢侈 / 出版。不用于仪表盘。

### 9.C layout 与间距
* **数学般完美**的内边距和外边距。不要带别扭空隙的浮动元素。
* **不要三列等大特性 card。** 泛化的"横向三张相同 card"特性行被禁止。使用两列锯齿、非对称 grid、scroll 固定或横向 scroll 替代。

### 9.D 内容与数据（"Jane Doe"效应）
* **不要泛化姓名。** "John Doe"、"Sarah Chan"、"Jack Su" → 使用有创意、真实、贴合地域的姓名。
* **不要泛化 avatar。** 不要 SVG"鸡蛋"或泛化用户图标 → 使用可信的照片占位或特定样式。
* **不要虚假完美数字。** 避免 `99.99%`、`50%`、`1234567`。使用有机、凌乱的数据（`47.2%`、`+1 (312) 847-1928`）。
* **不要初创低质品牌名。** "Acme"、"Nexus"、"SmartFlow"、"Cloudly" → 创造贴合语境、听起来真实的高端名称。
* **不要填充动词。** "Elevate"、"Seamless"、"Unleash"、"Next-Gen"、"Revolutionize" → 只用具体动词。

### 9.E 外部资源与 component
* **不要手写 SVG 图标。** 使用平台 overlay 允许的图标库。
* 手写装饰性 SVG 作为默认**强烈不推荐**（见第 4.8 节）。
* **不要手搭的假截图。** 禁止用样式化矩形拼一个假产品 UI 来模拟截图。使用真实图片、生成图片，或跳过预览。
* **不要坏掉的图库链接。** 使用 `https://picsum.photos/seed/{descriptive-string}/{w}/{h}`、生成的图片占位或实际 asset。
* **生产级整洁：** 代码视觉上干净、令人难忘、精雕细琢。

### 9.F 生产测试破绽（一律禁止）

这些模式来自真实的 LLM 生成落地页测试。它们是模型试图"显得有设计感"时默认输出的特征。除非简报明确要求其一，否则将其视为硬性禁令。

**Hero 与页首**
* **Hero 里不要版本标签。** `V0.6`、`v2.0`、`BETA`、`INVITE-ONLY PREVIEW`、`EARLY ACCESS`、`ALPHA`——禁止作为默认 eyebrow。仅当简报明确关于产品发布 / 预览状态时才可接受。
* **不要 "Brand · No. 01" 式副 eyebrow。** "Marrow · No. 01 · The 6-quart" 这类微元信息行。跳过它们。

**区块编号与微标签**
* **不要区块编号 eyebrow。** `00 / INDEX`、`001 · Capabilities`、`002 · Featured commission`、`06 · how it works`、`05 · The honest table`——禁止。eyebrow 应该用平实语言命名主题，而不是编号。
* **图片或 bento 磁贴上不要 `01 / 4` 式分页。** 如果用户能数数，就不需要标签。
* **不要 `Scroll · 001 Capabilities` 式 scroll 提示。** 一个简单的箭头或"Scroll"就够了；不要区块编号前缀。
* **不要 "Index of Work, 2018 - 2026" 式区间标签**作为 eyebrow。直接说这个区块是什么。

**分隔符与圆点**
* **中点（`·`）要限量。** 元数据条里每行最多 1 个。不要把它当成一切的默认分隔符（"foo · bar · baz · qux · quux"）。如果需要一套分隔符，优先用换行、发丝线或分栏。
* **不要在每个列表 / nav / badge 上都放装饰性彩色状态点。** "ONE Q4 SLOT OPEN" 前面、每个导航链接前面、每个任务行前面的彩色点——默认禁止。仅当该点传达真实语义状态（服务器状态、可用性标志）且克制使用时才可接受。

**Em-dash 与排版装饰**
* **不要 em-dash（`—`）作为设计元素或出现在任何地方。** 完整且没有商量余地的禁令见下方第 9.G 节。em-dash 字符在标题、eyebrow、胶囊、正文、引文、署名、图注、按钮文本和 alt 文本中都被禁止。使用普通连字符（`-`）。
* **不要用强制换行折断加斜体的标题**作为默认"设计手法"。"for thirty\<br\>*years.*" 这类拆分。标题首先应自然可读，仅当简报要求时才玩花样。
* **不要垂直旋转文字**（"INDEX OF WORK, 2018 - 2026" 旋转 90°）。代理商作品集陈词滥调。仅当简报明确是代理商 / Awwwards / 实验风且确有构图目的时才用。
* **不要十字准线 / 发丝 grid 线作装饰。** 只为让页面"显得有设计感"而画的垂直线和水平线——禁止。仅当它们组织真实内容时才用。

**假产品预览**
* **Hero 里不要手搭的假产品 UI**（假任务列表、假终端、用样式化矩形拼的假仪表盘）。这是 LLM 设计破绽第一名。使用真实截图、生成图片、真实 component 预览，或干脆不用。
* **假截图里不要假版本 footer**（"v0.6.2-rc.1"、"last sync 4s ago · main"）。毫无增益，AI 感爆棚。

**营销文案破绽**
* **不要 "Quietly in use at" / "Quietly trusted by"** 社会证明标题。使用自然语言："Trusted by"、"Used at"、"Customers include"，或者如果标志自己会说话就完全跳过标题。
* **引文、博客或 sidebar 区块不要 "From the field" / "Field notes" / "Currently on the bench" / "On our desks" / "Loose plates" 式诗意标签。** 读起来像装腔作势的匠人。使用平实的功能性标签（"Testimonials"、"Latest writing"、"Now working on"）或跳过标签。
* 正文里**不要 "We respect the French ones" 式**装谦逊的行业引用。俏皮且 AI 味重。
* 页眉 / footer**不要天气 / 地域条**（"LIS 14:23 · 18°C"），除非简报明确关于某地 / 跨时区分布的工作室。
* **eyebrow 下不要微元句子。** 像 *"Each of these is a feature we ship today, not a roadmap promise. The list will stay short on purpose."* 这样坐在区块标题下的句子是杂乱。Eyebrow + 标题 + 正文就够了。
* **不要泛化步骤标签。** "Stage 1 / Stage 2 / Stage 3"、"Step 1 / Step 2 / Step 3"、"Phase 01 / Phase 02 / Phase 03"、"Pass One / Pass Two / Pass Three"。禁止。实际的步骤内容就是标签。如果必须展示进展，直接用动宾短语（"Install"、"Configure"、"Ship"），而不是 "Stage 1: Install"。

**胶囊、标签与版本戳**
* **不要叠加在图片上的胶囊 / 标签 / 标记。** 不要在照片上叠加带 `Brand · 02`、`PLATE · BRAND`、`Field notes - journal` 之类标签的文本片。要么让图片自己说话，要么在图下方（图片之外）直接加图注。
* **不要装饰性摄影署名图注。** 图库 / picsum 图片下的 `Field study no. 12 · Ines Caetano`、`Plate 03 · House archive`、`Frame XII · 35mm` 之类字符串是装腔作势。仅当确有真实摄影师因真实照片（经许可）被署名时才允许摄影署名。否则：跳过图注，或使用一行功能性图注（"The 6-quart, in Sage."）。
* **营销页不要版本 footer。** `v1.4.2`、`Build 0048`、`last sync 4s ago · main` 之类 footer 字符串是 CLI / 开发工具的设备信息，不是落地页内容。营销 / 落地 / 作品集页面上禁止。
* **不要 "Reservation 412 of 800" 式实时库存计数器**作装饰。仅当简报明确是限量候补名单且有真实数据时才用。

**装饰文字条**
* **hero 底部不要装饰文字条。** 横贯 hero 底部的小号 monospace 大写条，如 `BRAND. MOTION. SPATIAL.`、`TYPE / FORM / MOTION`、`DESIGN · BUILD · SHIP`、`ESTD. 2018 · LISBON · BRAND. MOTION. SPATIAL.`，是代理商作品集陈词滥调。默认禁止。仅当该条承载真实可导航链接（粘性底部 nav）或真实状态信息（cookie 横幅、文档站的构建信息）时才可接受。
* **区块标题里不要漂浮的右上角副文本。** 模式：区块有一个巨大的左对齐标题；同一区块标题的右上角漂浮着一小段说明文字，与任何东西都没有清晰对齐。那个漂浮物就是破绽。要么把副文本直接放在标题下方，要么构建干净的两栏标题（左：标题，右：对齐正文），而不要角落里的迷你段落。

**列表、分隔线与评分**
* **长列表 / 规格表的每一行不要同时加上边框和下边框。** 选一种（行间下边框或组上方边框）并克制使用。每行下都有一条发丝线的 10 行规格表是最懒的 layout——替代 UI component 见第 4.9 节。
* **不要带填充背景轨道的评分 / 进度条**作对比视觉。如果需要展示 "X out of Y" 对比，优先数字 + 小图标，或一条不带背景轨道的小型内联条。上面带部分填充的大号浅灰轨道，在落地页上是仪表盘 UI 的杂乱。

**地域、时间、scroll 提示**
* **99% 的简报都禁止地域 / 城市名 / 时间 / 天气条。** hero 里的 "Lisbon, working with founders"、footer 里的 "1200-690 Lisbon, Portugal"、nav 里的 "Lisbon 14:23 · 18°C"。这些都是代理商作品集装饰破绽。仅在以下情况允许：简报明确描述一个跨时区分布的全球工作室，或旅行主题品牌，或真实的实体场所。footer 单提一次联系地址可以；氛围感地域条不行。
* **scroll 提示被禁止。** `Scroll`、`↓ scroll`、`Scroll to explore`、`Scroll to walk through it`、动画鼠标滚轮图标。如果用户还没 scroll，他们正在看 hero。他们知道什么是 scroll。viewport 底部不需要标签。
* **默认零装饰状态点。** nav 项、列表行、badge、状态标签前面的彩色点是破绽。仅当传达真实语义状态（真实服务器状态的实时指示、实时可用性标志）且每页区块限一个时才可接受。

### 9.G EM-DASH 禁令（违反率最高的破绽）

**Em-dash（`—`）被完全禁止。** 它是 LLM 的标志性风格拐杖，也是生产测试中排名第一的视觉破绽。没有"限量使用"的宽限，没有"自然语言频率"的宽限，没有"正文里可以"的宽限。一概没有。

* **标题中禁止。** 使用句号或逗号。
* **eyebrow / 标签 / 胶囊 / 按钮文本 / 图片图注 / 导航项中禁止。** 用换行、分栏或发丝线替代。
* **正文中禁止。** 重构句子：用句号拆成两句，或用逗号、括号、冒号。
* **引文署名中禁止。** 使用带空格普通连字符（` - `）或换行 + 更小字重名字。
* **作为分隔符时，en-dash 形式（`–`）同样禁止。** 日期区间（`2018-2026`）用连字符。数字区间（`€40-80k`）用连字符。

页面上唯一允许的破折号字符是：
* 普通连字符 `-`（用于复合词、区间、标记中的行分隔线）
* 数学中的负号（`-5°C`）

如果输出中任何用户可见的地方出现一个 `—` 或 `–`，输出即未通过起飞前检查，必须重写。

这条规则没有商量余地。过去当表述为"克制使用"时，智能体一直无视 em-dash 的限制。这里的表述是二元的：零 em-dash。

## 10. 参考词汇表（智能体应知的模式名称）

这是一份词汇表，不是库。智能体应该知道这些模式名称，以便围绕它们交流、带着它们做设计，并在设计解读要求时取用它们。**实现与代码草稿存放在 Block Library（第 12 节）中，该库会迭代填充。** 各平台的动画库选择见平台 overlay。

### Hero 范式
* **非对称分屏 Hero**——一侧文字，另一侧 asset，充足留白。
* **编辑宣言 Hero**——大字排版，无 asset，近乎海报。
* **视频 / 媒体蒙版 Hero**——文字作为蒙版镂空在视频背景上。
* **动感字体 Hero**——动画字体排版作为主视觉。
* **幕布揭开 Hero**——Hero 随 scroll 如幕布般分开。
* **scroll 固定 Hero**——Hero 保持固定，内容在其后 scroll。

### 导航与菜单
* **Mac OS Dock 放大**——边缘导航，图标 hover 时流畅缩放。
* **磁吸按钮**——向光标吸引。
* **粘液菜单**——子项如粘稠液体般分离。
* **灵动岛**——用于状态 / 提醒的变形胶囊。
* **情境径向菜单**——在点击处展开的圆形菜单。
* **浮动快速拨号**——FAB 弹开为弧形次级操作。
* **巨型菜单展开**——全屏下拉，内容错峰淡入。

### layout 与 grid
* **Bento grid**——非对称磁贴分组（Apple 控制中心）。
* **瀑布流 layout**——错落 grid，无固定行高。
* **Chroma grid**——带细微动画 gradient 的边框 / 磁贴。
* **分屏 scroll**——两半向相反方向滑动。
* **粘性堆叠区块**——scroll 时固定并堆叠的区块。

### card 与容器
* **视差倾斜 card**——跟踪鼠标坐标的 3D 倾斜。
* **聚光边框 card**——光标下的边框发光。
* **玻璃拟态面板**——带内部折射的磨砂玻璃。
* **全息箔 card**——hover 时虹彩 gradient。
* **Tinder 滑动堆叠**——物理 card 堆叠，滑走。
* **变形 modal**——按钮展开为自身的对话框。

### scroll 动画
* **粘性 scroll 堆叠**——card 粘住并物理堆叠。
* **横向 scroll 劫持**——垂直 scroll → 横向平移。
* **Locomotive / 序列 scroll**——视频 / 3D 序列绑定 scrollbar。
* **缩放视差**——中央背景图随 scroll 缩放。
* **scroll 进度路径**——沿 scroll 绘制 SVG 线条。
* **液态滑动过渡**——如粘稠液体的页面过渡。

### 画廊与媒体
* **穹顶画廊**——3D 全景画廊。
* **Coverflow carousel**——带斜边的 3D carousel。
* **拖拽平移 grid**——无边界可拖拽画布。
* **accordion 图片滑块**——hover 展开的窄条。
* **hover 图片拖尾**——鼠标留下弹出图片拖尾。
* **故障效果图片**——hover 时 RGB 通道偏移。

### 字体排版与文字
* **动感跑马灯**——随 scroll 反转的无限文字带。

## 11. 改版协议

本技能处理**全新构建和改版**。对模式分类错误是糟糕改版输出的最大单一来源。

### 11.A 检测模式（第一步）
* **全新**——无现有站点，或已批准全面重构。旋钮基线来自第 1 节。
* **改版 - 保留**——在不破坏品牌的前提下现代化。先审计、提取品牌 token、渐进演化。
* **改版 - 重构**——在现有内容之上换新视觉语言。视觉按全新处理；保留内容与信息架构（IA）。

如有歧义，**问一次**：*"这次改版应该保留现有品牌，还是视觉上从零开始？"*

### 11.B 动手前先审计
在提出变更前记录当前状态：
* **品牌 token**——主 / 强调色、字体栈、标志处理、radius。
* **信息架构**——页面树、主导航、关键转化路径。
* **内容区块**——现存什么、什么在发挥作用、什么是填充。
* **要保留的模式**——标志性交互、可辨识的 hero、文案语气。
* **要淘汰的模式**——AI 低质破绽、坏 layout、死链、泛化图库图片、性能陷阱。
* **现有站点的旋钮读数**——推断当前的 `DESIGN_VARIANCE` / `MOTION_INTENSITY` / `VISUAL_DENSITY`。那是你的起点，而不是基线。
* **SEO 基线**（Web 改版）——当前排名页面、meta 标题、结构化数据、OG card。**SEO 迁移是改版的第一大风险。**（Flutter 应用改版的对应物是应用商店素材与深链，见 taste-flutter overlay。）

### 11.C 保留规则
* **除非被要求，不要更改信息架构。** 为 SEO 和肌肉记忆保持页面 slug、锚点 ID、主导航标签稳定。
* **在应用第 4.2 节之前先提取品牌色。** 已经是紫色的品牌保持紫色——应用 LILA 规则的覆盖条款。
* **保留文案语气**，除非要求重写。视觉现代化 ≠ 内容重写。
* **尊重现有无障碍成果。** 不要倒退焦点状态、alt 文本、键盘导航、对比度。
* **尊重现有埋点事件。** 不要重命名下游追踪所依赖的按钮、表单字段、区块 ID。

### 11.D 现代化杠杆（优先级顺序）
按顺序应用——简报满足即停：
1. **字体排版刷新**——单位风险下最大的视觉提升。
2. **间距与节奏**——加大区块内边距，修正垂直节奏。
3. **色彩重校准**——降饱和、统一中性色、保留品牌强调色。
4. **动效层**——给现有 component 添加与 `MOTION_INTENSITY` 匹配的微交互。
5. **Hero 与关键区块重构**——用第 10 节词汇表重构漏斗顶部。
6. **整体替换区块**——仅当现有区块无可救药时。

### 11.E 决策树：定向演化 vs 全面改版
* IA、内容和 SEO 健全 → **定向演化**（杠杆 1-4）。约 40% 的风险获取约 70% 的价值。
* 视觉债是结构性的（IA 损坏、无设计系统、移动端损坏）→ **全面改版**并严格保留内容。
* 品牌本身在变 → **全新**。

### 11.F 禁止静默改变的东西
未经用户明确批准，禁止修改：
* URL 结构 / 路由 slug。
* 主导航标签。
* 表单字段名或顺序（破坏埋点 + 自动填充）。
* 品牌标志或字标。
* 现有法律 / 同意 / cookie 文案。

参考词汇表（第 10 节）为模式命名。Block Library 用真实 props、真实动效规格和真实代码草稿来实现它们。


`stack` 字段列出平台技术栈标识。Web 区块示例见上；Flutter 区块使用如 `["flutter", "dart", "google_fonts"]`。

### 12.C 必需的正文小节
1. **视觉草图**——layout 的简短 ASCII 或描述。
2. **Props API**——component 的接口。
3. **代码草稿**——最小可用实现（静态部分用平台的默认渲染方式，动效隔离到专门的叶子单元）。
4. **窄屏回退**——`< 768px`（或手机宽度）的显式坍缩规则。
5. **动效变体**——每个 `MOTION_INTENSITY` 区间一个变体（1-3、4-7、8-10）。减弱动效回退须显式。
6. **dark mode 说明**——该区块专属的 token 策略。
7. **反模式**——该区块常见的出错方式。
8. **参考**——指向生产中真实示例的链接。

### 12.D Block-Library 纪律
* 每文件一个区块。不要多区块文件。
* 每个区块必须独立可用（放进页面即可用）。
* 每个区块必须通过起飞前检查（第 14 节 + 平台 overlay 的检查项）。
* 依赖某个设计系统的区块，放在 `blocks/<category>/<name>--<system>.md` 下（例如 `feature/bento-grid--material.md`）。

## 15 完整输出强制

### 基线

将每项任务视为生产关键任务。部分输出就是损坏的输出。不要为简洁而优化——要为完整而优化。如果用户要求完整文件，就交付完整文件。如果用户要求 5 个 component，就交付 5 个 component。没有例外。

### 禁止的输出模式

以下模式属于严重失败。禁止产生它们：

**在代码块中：** `// ...`、`// rest of code`、`// implement here`、`// TODO`、`/* ... */`、`// similar to above`、`// continue pattern`、`// add more as needed`、代替被省略代码的裸 `...`

**在正文中：** "Let me know if you want me to continue"、"I can provide more details if needed"、"for brevity"、"the rest follows the same pattern"、"similarly for the remaining"、"and so on"（当替换实际内容时）、"I'll leave that as an exercise"

**结构性捷径：**当要求完整实现时输出 skeleton。只展示首尾两个部分而跳过中间。用一个示例加一段描述来替换重复逻辑。描述代码应该做什么而不是编写代码。

### 执行流程

1. **范围**——通读完整请求。数清预期有多少个不同的交付物（文件、函数、分区、答案）。锁定这个数字。
2. **构建**——完整生成每个交付物。不得有部分草稿，不得有"你以后可以扩展这个"。
3. **交叉检查**——在输出之前，重新阅读原始请求。将你的交付物数量与范围数量对比。若有任何缺失，在响应之前补上。

### 处理长输出

当响应接近 token 上限时：

- 不要压缩剩余部分以强行塞入。
- 不要直接跳到结论。
- 以完整质量写到一个干净的 breakpoint（函数末尾、文件末尾、分区末尾）。
- 以如下内容结尾：

```
[PAUSED — X of Y complete. Send "continue" to resume from: next section name]
```

收到 "continue" 时，从你停止的地方精确继续。不重述、不重复。

### 快速检查

在最终确定任何响应之前，验证：
- 输出中任何位置都不出现上面列表中的禁止模式
- 用户要求的每一项都已存在并完成
- 代码块包含实际可运行的代码，而非对代码会做什么的描述
- 没有任何内容为了节省空间而被缩短
