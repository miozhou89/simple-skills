## What it does

性能分析与优化的指南。先把问题按「分析流程」走一遍：**数量级成本估算 → 剖析定位 → 优化 → 验证**，再按杠杆从高到低从「优化技术目录」（算法改进、内存表示、减少分配、避免不必要工作、并行化与同步、API 设计、Protobuf、批量操作）取用对应手段。每个技术的共同逻辑是减少昂贵的操作（缓存未命中、内存分配、网络/磁盘、锁、重复计算），而非让廉价算术更快。

**定义性约束**：先估算和剖析拿数据，再动手优化；优化后用微基准守住回归，不靠感觉断言。

## When to reach for it

- **调用方式**：当用户讨论系统或代码性能、请求优化或提速、剖析（profiling）、降低延迟、减少内存占用、排查瓶颈，或问「这段代码哪里慢、该怎么优化」时，模型自动取用。
- **触发边界**：若用户报告的是「最近变慢了」的回归，优先走 diagnosing-bugs；本 skill 面向主动的性能分析与优化工作。

## It's working if

- 优化前先做了数量级成本估算，明确了瓶颈在哪些昂贵操作上。
- 用剖析工具（pprof/perf）或微基准定位，而不是靠猜。
- 每个优化手段都能对应到技术目录里的原理，并说明消除了什么成本。
- 优化后重新剖析 + 微基准验证，防止回归。

## Where it fits

- **角色**：model-invoked 的工程维护 skill，与 diagnosing-bugs 相邻——后者处理「坏了/变慢了」的回归，本 skill 处理主动的性能分析与优化。
- **邻居**：diagnosing-bugs（性能回归）、code-review（评审时可引用其技术目录检查性能）、improve-codebase-architecture（架构层面的深化，本 skill 聚焦运行时成本）。
- **地图**：ask-route 的「代码库健康」部分统领其路由。
